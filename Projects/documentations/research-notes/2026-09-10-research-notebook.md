# AK550 Noodoe 커스텀 펌웨어 연구노트

> **2026-09-11 후속 기록:** 12V 두 접점 중 IGN을 식별해 ON/OFF 문제를 해결했고, 6핀 CN3의 1번에서 GND 유지 시 기동 억제·해제 후 초기 부팅이 관측됐다. NRST 유력 후보이며 전원 레일 및 MCU NRST와의 연결 확인은 남아 있다. 이 문서의 과거 임시 CN 번호와 구분해 [새 관측 기록](2026-09-11-ign-cn3-reset-candidate.md)을 참고한다.

**기록 기준: 2026-09-10 KST · 대상: 2017 AK550 도너 계기판·Noodoe 세트**

서비스 종료 이후에도 Noodoe를 사용할 수 있도록 순정 자료를 보존하고, 차량 인터페이스와 부팅·업데이트 구조를 파악해 커스텀 펌웨어 개발 기반을 마련한다. 이 문서는 오늘까지의 하드웨어·펌웨어 연구를 중심으로 기존 분석과 실물 관측을 통합한 기록이다. 과거 문서와 해석이 달라진 부분은 최신 관측을 반영했다.

**현재 도달점:** 순정 APK·OTA와 도너의 USB 노출 저장공간을 확보했다. 계기판↔Noodoe UART의 통신 조건, 양방향 역할, 프레임 구조를 확인했고, ODO와 연료 0·1칸을 실물 표시와 대조했다. 연결부에서는 UART 외에 버튼 신호도 찾았다. **Noodoe의 SWD 접점과 내부 플래시·부트로더 백업은 아직 확보하지 못했다.**

## 1. 기록의 기준과 대상

| 근거 구분 | 이 노트에서 뜻하는 것 |
|---|---|
| 원본 검증 | 로컬 BIN·APK·USB 이미지·CSV·시리얼 파일을 직접 분석한 결과 |
| 정적 분석 | 특정 OTA 또는 APK의 코드가 수행하는 동작. 도너의 실행 버전과 동일하다는 보장은 별도 |
| 실물 관측 | 사용자가 수행하고 보고한 측정·표시·배선 변경. 대응 원시 파일이 있으면 별도로 대조 |

실차는 **2018년식 AK550**, 벤치 연구용 구입품은 **2017년식 AK550의 차량 계기판과 Noodoe 모듈 세트**다. 두 장치는 별도 보드이며 다음 경계를 계속 구분한다.

```text
차량의 센서·하네스 ── 차량 계기판 ── Noodoe 모듈 ── Bluetooth ── 휴대전화
                     │               │
                  TOOL0 / RESET     SWD 탐색 대상
```

- 차량↔계기판 핀아웃은 사용자가 확보했다. SPEED·FUEL·TEMP는 이쪽 입력을 조사한 기록이다.
- 계기판↔Noodoe는 세 커넥터를 조사해 UART·버튼 반응·전압을 파악했다. 이 노트에는 아직 실제 접점 번호와 관찰 방향을 갖춘 완성 도면이 수록되지 않았다.
- 도너 Noodoe에서 160개 이상 핀을 가진 큰 IC를 관찰했으나, **MCU 전체 마킹·패키지·실제 플래시 용량·현재 설치 펌웨어·RDP 상태는 미확정**이다.
- SR1.5 V5.16의 코드·메모리·주변장치 구성이 STM32F429 계열과 합치한다. 이를 실물 칩 식별의 대체물로 사용하지 않는다.
- ‘CV3 계열 외에 Noodoe 하드웨어가 모두 같다’는 작업 가설이다. 확보한 OTA에는 여러 계열이 있으므로 다른 모델·연식에 같은 핀맵이나 펌웨어를 바로 적용할 근거는 아니다.

보유 장비는 Agilent 디지털 오실로스코프 2대(54622D 포함), 무전기용 전원 공급기, ANENG 멀티미터, 디버거, ATmega328P를 제거한 순정 Uno다. 스코프 측정에는 악어클립과 Arduino 점퍼선을 사용했다. 디버거의 정확한 모델은 이 기록에서 확인되지 않았다.

### 2.2 도너 USB 보존

처음에는 USB-B만 연결했을 때 모듈이 동작하지 않았다. 이후 USB 저장장치가 인식됐고, 일부 파일은 보이지만 일부 경로는 읽을 수 없었다. USB 단독 전원만으로 정상 구동할 수 있는지는 확정하지 않았다.

| 항목 | 결과 |
|---|---|
| 장치 식별 | VID `0483`, PID `5720`, 볼륨명 `NOODOE` |
| 노출 용량 | 133,693,440바이트 = 127.5MiB |
| 원본 보존 | 노출 볼륨을 두 번 읽어 로컬 이미지로 저장. 두 이미지 바이트 단위 일치 |
| 정상 파일 복사 | 193개: PNG 176, JPEG 9, JSON cfg 4, Windows 메타데이터 4 |
| 파일시스템 | FAT 연결 오류와 디렉터리 교차 연결을 확인. 두 FAT가 같아도 정상은 아니었음 |
| 추가 추출 | 로컬 이미지에서 순정 manifest와 내용 해시가 맞는 고유 콘텐츠 965개 확보 |

965는 정상 설치 파일 수나 전체 디렉터리 복구 수가 아니다. 참조 manifest와 맞는 내용이 이미지 안에 존재했다는 집계이며 이전·중복 배치가 포함될 수 있다. 손상 원인과 발생 시점은 확인하지 못했다.

V5.16의 USB MSC 경로는 **SPI5 외부 NOR**에 연결되고, 광고 용량이 실물과 일치한다. 코드상 128MiB 중 앞 127.5MiB를 USB로 노출하며 마지막 512KiB는 제외한다. 따라서 이번 백업은 **외부 저장공간의 USB 노출 부분**이다. STM32 내부 플래시나 Noodoe 부트로더를 백업한 것은 아니다.

도너에서 JSON cfg와 일반 PNG/JPEG 기반 콘텐츠를 확인했다. 복구한 리소스 설정의 5.14 표기는 리소스 계열의 단서이며, 실행 펌웨어가 5.14 또는 5.16이라는 증거는 아니다. 전 소유자의 이미지와 불필요한 계정 정보는 연구노트에 재게시하지 않는다.

두 읽기는 마운트된 장치에서 수행됐다. 직접 실행한 장치 쓰기·포맷·파일시스템 복구는 없지만, 연결 전후의 OS·장치 배경 쓰기까지 없었다고 단정하지 않는다.

## 3. UART 확보: 초기 잡음에서 정상 프레임까지

### 3.1 캡처 조건과 접지 변경

사용자는 계기판과 Noodoe를 연결해 정상 동작시킨 상태에서 각각의 신호선을 관측했다. Uno는 메인 MCU를 제거한 USB-UART 브리지로 사용했다. 이 구성에서 수신선은 **Uno D1/TX → USB 브리지 RX**이며 공통 GND를 연결한다. D0/RX는 브리지의 출력이므로 수동 수신에는 연결하지 않는다.

초기에는 공통 접지를 브레드보드의 파란색 마이너스 스트립으로 연결했다. 이후 **Uno GND선을 계기판 GND선에 직접 연결**했고 정상 프레임이 확보됐다. 이 변경과 수신 개선은 중요한 관측이다. 다만 당시의 정확한 접촉 불량 지점이나 각 접지선의 임피던스를 측정한 것은 아니다.

아래 집계는 로그 행의 RX 바이트를 이어 붙여 검사한 결과다. 시리얼 프로그램의 한 행을 프레임 하나로 취급하지 않았다.

| 캡처 | RX 바이트 | 정상 프레임 | 핵심 결과 |
|---|---:|---:|---|
| `040831.tsv` | 4,264 | 0 | `55` 3,598개, 84.38%. 정상 F5 프레임 없음 |
| `040913.tsv` | 9,121 | 0 | `55` 7,771개, 85.20%. 정상 F5 프레임 없음 |
| `UPPERPIN.tsv` | 186 | 30 | 정상 A1 30개, 체크섬 실패 후보 1개 |
| `LOWERPIN.tsv` | 1,508 | 116 | 정상 21 프레임 116개 |
| `FROMDASH-GAS1` | 513 | 33 | 정상 21 프레임 33개, 체크섬 실패 후보 6개 |
| `lower-fuel0.tsv` | 299 | 23 | 정상 21 프레임 23개 |

파일명은 공통 접두부 `diserial-COM11-115200-8N1-`를 생략했다. 초기 두 파일에는 날짜 접두부 `20260910-`가 추가로 붙는다. GAS1 원본은 확장자가 없다. 원본과 분석 경로는 §10에 연결했다.

**초기 `55` 편중을 정상 프리앰블이나 별도 프로토콜로 해석하지 않는다.** 수신 바이트값의 비트 반전·비트 순서 변경·특정 바이트 제거 등으로 유효 프레임을 복원하지 못했고, 이후 정상 캡처와 맞지 않았다. 이 바이트 가공 검사는 원파형 극성을 뒤집어 다시 디코딩한 시험과 동등하지 않다. 불량 프레임을 임의로 고쳐 차량 데이터로 사용하지 않는다.

### 3.2 54622D 플로피 CSV의 독립 확인

`PRINT_01.CSV`는 500ns 간격 2,000점, 약 1ms 구간이다. 사용자가 측정한 약 8µs 비트 폭과 일치하게 **115200 baud, 8N1, 비반전**으로 다음 바이트가 복원됐다.

```text
F5 A1 02 01 07 50
```

여러 판정 임계값에서 같은 결과가 나왔고 XOR도 맞았다. 전이 시점으로 맞춘 비트 주기는 약 8.67µs다. 이를 스코프 샘플 해상도를 넘어서는 정밀 보레이트 측정값으로 취급하지 않는다.

LOW 구간 내부 값은 대략 1.25–3.25V, HIGH는 4.75–5.00V였다. LOW가 높고 흔들리는 현상 자체는 CSV에 남아 있다. **이 스코프 캡처에는 Uno가 신호선에 연결되지 않았으므로 Uno 부하가 원인이라고 설명할 수 없다.** 악어클립·점퍼선·접지 경로가 사용된 측정이며, 실제 IC 출력의 LOW 전압이나 정확한 잡음 원인을 확정하지 못했다. 단순 감쇠 링잉만으로도 충분히 설명되지 않았다.

`PRINT_00.CSV`는 밀리볼트 수준의 다른 관측이다. 이것을 반대 방향 UART 캡처라고 지정하지 않는다.

## 4. 계기판↔Noodoe 프로토콜의 현재 지도

### 4.1 방향과 프레임

실물 신호는 사용자 측정 기준 **5V UART**, 통신 조건은 **115200 8N1**이다. V5.16의 UART5 설정과 맞는다. 코드상의 PC12/TX·PD2/RX 후보는 MCU 신호명이므로 커넥터 접점 번호와 혼동하지 않는다.

| 사용자가 붙인 위치명 | 확인한 기능 | 정상 반복 프레임 | 로그상 대표 간격 |
|---|---|---|---|
| UPPERPIN | Noodoe TX → 계기판 RX | `F5 A1 02 01 07 50` | 중앙값 약 401ms |
| LOWERPIN | 계기판 TX → Noodoe RX | `F5 21 09 00 00 00 00 7B 8E 00 00 00 28` | 중앙값 약 99ms |

이 위치명은 촬영 방향이나 공식 CN 핀 번호를 대신하지 않는다. 간격은 PC 로그 타임스탬프 기준이며 두 방향을 동시에 캡처한 결과도 아니다. 긴 로그 공백이나 체크섬 실패 비율을 실제 선로의 손실률로 바로 환산하지 않는다.

```text
F5 | CMD | LEN | PAYLOAD[LEN] | XOR

XOR = F5부터 PAYLOAD 마지막 바이트까지의 바이트별 XOR
전체 프레임의 XOR = 00
```

V5.16은 UART5의 바이트 단위 RX 인터럽트에서 F5 파서로 전달한다. DMA 설정의 존재만으로 이 경로가 DMA 링 수신이라고 설명했던 것은 정정했다. Bluetooth 컨트롤러와 통신하는 USART1/HCI는 별도 인터페이스이며, 보레이트를 다시 설정하는 경로가 있다.

### 4.2 CMD 21/22 페이로드

아래 offset은 **payload 시작을 0으로 센 값**이다. CMD21의 소비 길이는 9바이트, CMD22는 11바이트다.

| offset | 정적 분석과 관측 | 확정 범위·남은 점 |
|---|---|---|
| 0 | 속도 정수 km/h 처리 | 정상 캡처는 0. 실물 1km/h와 `01`을 같은 캡처에서 짝지은 검증은 아직 없음 |
| 1 | 미확인 바이트 | 특정 센서·상태와 대응하지 못함 |
| 2 | 공용 `BatteryWidget` / `fuel_battery` 잔량 raw 소비 | 실제 AK550 연료 0·1칸 파일 모두 `00`. 이 바이트를 AK550 연료량으로 확정하지 않음 |
| 3 하위 니블 | GAS1에서 1, fuel0에서 0 | 실물 연료 표시 1칸·0칸과 대응 확인 |
| 3 상위 니블 | 두 연료 파일 모두 5 | 실물 총 5칸과 맞아 ‘전체 칸 수’ 후보지만 아직 미확정 |
| 4–7 | little-endian 32비트 ODO | `7B 8E 00 00` → 36,475. 사용자가 실제 ODO 36,475km와 일치 확인 |
| 8 | raw에서 40을 빼 16비트 상태에 저장 | 온도형 산술의 근거만 있음. 실제 센서·단위·표시 경로 미확정, 활용 보류 |
| 9–10 | CMD22만 존재하는 little-endian 16비트 값 | 의미 미확정 |

payload2의 공용 위젯 분류는 0, 1–20, 21–40, 41–60, 61–80, 81 이상이다. 이것이 실제 AK550의 연료 퍼센트라는 뜻은 아니다. payload3의 니블 분해는 코드로 확인했지만 Noodoe 화면에서 두 니블을 어떻게 사용하는지는 확정하지 못했다.

### 4.3 그 밖의 명령과 미확인 필드

- **RX 41 / 42:** 코드가 각각 250 / 71바이트를 소비하는 경로를 확인했다. 41은 캐시 후 휴대전화 SPP 16으로 분할 전달되고, 42는 SPP C6으로 전달된다. 내부 필드 해석과 실제 AK550 송신 여부는 미확정이다.
- **TX A1:** payload는 `{01, 조도 분류 인덱스}`다. 상세 내용은 §5.3에 기록한다.
- **TX 01:** 인수 1–4를 1/2/4/8로 바꾸는 경로와 `04`, `00` 송신 사례가 코드에 있다. 이를 네 버튼의 비트마스크로 판정할 근거는 없다. 물리 버튼 선 3개의 발견과도 별도로 검증해야 한다.
- **수신 길이:** F5 파서는 허용 CMD와 LEN≠0을 검사하지만 각 명령의 정확한 길이를 검증하지 않는다. 소비 길이와 파서의 수락 조건을 구분한다. 짧은 payload 처리의 정적 결함 후보가 곧 코드 실행이나 플래시 덤프 방법으로 입증된 것은 아니다.

RPM·TPMS·배터리 전압·방향지시등·브레이크 상태 등을 특정 필드에 대응시키지 못했다. 위젯명이나 명령의 존재만으로 해당 정보가 실제 UART에 있다고 확정하지 않는다.

근거: [UART 페이로드 지도](2026-09-09-ak550-uart-payload-map.md), [UART·업데이트 감사](2026-09-09-ak550-firmware-uart-boot-review.md).

## 5. 입력별 실험 기록

### 5.1 SPEED: 접지 접촉·분리에 반응

SPEED 핀을 GND에 접촉하고 떼는 동작으로 차량 계기판에 1km/h가 표시됐다. 입력 에지·펄스를 속도로 처리한다는 강한 관측이다. 손 접촉에는 바운스가 있으므로 이것만으로 펄스당 거리, 주파수–속도 환산식, 입력 임계값·허용 전압을 정하지 않는다. 이후 제어된 펄스와 물리 표시·UART payload0을 함께 기록할 필요가 있다.

### 5.2 FUEL: 표시 0칸과 1칸의 대응 확보

초기 시험에서 FUEL 쪽에 12V를 접촉하자 스파크와 리셋이 있었고, FUEL+/−를 직결하자 잔량 표시가 변하다 꺼졌다는 보고가 있었다. 이 관측만으로 손상 여부나 특정 고장 코드를 판정하지 못했다. 해당 입력은 유량계보다 **연료잔량 센더 입력**으로 기록하는 것이 정확하다.

제조사 AK550 정비매뉴얼의 센더 규격은 Full **100Ω ±3%**, Empty **2,400Ω ±3%**다. 배선도에서 실제 FUEL 두 선이 해당 센더에 대응하는지 연결해 확인해야 한다. 외부 12V 직접 주입이나 0Ω 직결은 정상 센더 범위 시험으로 취급하지 않는다. 근거: [KYMCO 정비매뉴얼 재게시본 §6-23](https://www.manualslib.com/manual/1968932/Kymco-Ak-550.html?page=210), [§6-24 저항 규격](https://www.manualslib.com/manual/1968932/Kymco-Ak-550.html?page=211).

이후 서로 다른 실제 표시 상태에서 다음 원본을 확보했다.

```text
표시 1칸 / GAS1 정상 33개:
F5 21 09 | 00 00 00 51 7B 8E 00 00 00 | 79

표시 0칸 / fuel0 정상 23개:
F5 21 09 | 00 00 00 50 7B 8E 00 00 00 | 78
offset      0  1  2  3  4  5  6  7  8
```

**payload3만 `51 ↔ 50`으로 달라졌고 체크섬이 그에 맞게 달라졌다.** payload2는 두 경우 모두 0, ODO는 모두 36,475였다. 따라서 현시점의 직접 대응은 ‘하위 니블 1 ↔ 실물 1칸, 하위 니블 0 ↔ 실물 0칸’이다. 2–5칸, 비선형 잔량 변화, 오류 상태는 추가 관측 대상이다.

GAS1의 체크섬 실패 6개는 이 결론에서 제외했다. 그 안에서 달라 보이는 속도·ODO를 실제 상태 변화로 취급하지 않는다. GAS1 파일은 이미 1칸 상태로 시작하므로 0→1 전이 순간을 포착한 기록도 아니다. 초기 LOWERPIN의 payload3=`00`은 이번 빈 연료 표시의 `50`과 다르므로 같은 상태로 합치지 않는다.

근거: [GAS1·fuel0 원본 비교](2026-09-10-fromdash-gas1.md), [입력 관측과 센더 문서 대조](2026-09-10-input-observations.md).

### 5.3 조도: A1은 7로 반복되지만 고장은 미판정

UPPERPIN의 정상 프레임은 `F5 A1 02 01 07 50`으로 반복됐다. 사용자는 빛을 바꿔도 값이 달라지지 않았고 밝기 조절이 동작하지 않는 것처럼 보였다고 보고했다.

정적 분석상 A1의 `07`은 Noodoe 자체 조도 분류의 **저장된 인덱스**다. 원시 lux나 밝기 70%가 아니다. 센서 코드에는 OPT3001의 식별값·계산 방식과 맞는 경로가 있지만 실제 부품 마킹은 확인하지 않았다.

- 조도 이벤트에서 센서를 읽고 분류·캐시를 갱신하는 경로와, UART 수신 횟수에 따라 A1을 보내는 경로는 별도다.
- 확인한 상태에서는 유효 수신 4회마다 A1을 보내며, 약 100ms 수신·400ms 송신 관측과 합치한다.
- 센서 읽기 실패·미준비 또는 분류 실패 시 이전 캐시가 유지될 수 있다. **함수의 상태 코드 7이 A1의 단계 7로 복사되는 것은 아니다.**
- 분류 임계값 원천은 OTA에 없는 `0x0800C040–0x0800C067`이다. 실제 lux 경계와 도너의 현재 설정을 재현하지 못했다.
- 확인한 경로의 자동/수동 백라이트 분기는 인덱스 저장 뒤에 있다. 수동 모드만으로 A1 갱신 정지를 설명할 수 없다.

따라서 입사광이 같은 분류 구간에 머문 경우, 센서 읽기·이벤트·분류 문제, 도너 버전 차이를 아직 구분하지 못한다. **A1=7 반복만으로 조도 센서 고장을 확정하지 않는다.**

근거: [조도 관측과 갱신 조건](2026-09-10-input-observations.md), [원시 코드 감사](../analysis/2026-09-10-input-observations/light/README.md).

### 5.4 TEMP: 저항에 따른 핀 전압 변화, UART 연동은 보류

발견한 것은 센서 실물이 아니라 **TEMP+ / TEMP− 핀**이다. 센서 품번이나 센서 자체는 없다. 사용자는 한 핀 약 5V, 다른 핀 약 0V를 보고했다.

103 가변저항은 **가운데 다리(와이퍼)를 TEMP−, 한쪽 끝 다리를 TEMP+**에 연결하고 스코프 +를 TEMP+ 노드에 댔다. 따라서 세 단자 분압기의 자유 와이퍼를 측정한 것이 아니라, 계기판 입력 양단에 두 단자 가변 부하를 걸고 입력 노드 전압을 측정한 구성이다. 회전에 따라 그 전압이 내려갔다.

이는 외부 저항에 따라 전압이 변하는 바이어스 회로와 맞는다. 아날로그 센서 입력 후보지만 ADC 연결·NTC 특성·온도 단위까지 확인된 것은 아니다. 이후 사용자는 **가변저항을 돌려도 UART 프레임이 전혀 변하지 않았다**고 보고했다. 해당 시험의 별도 원시 캡처와 저항·전압·유지 시간 표는 확보하지 않았다.

**결정: TEMP 입력 활용과 payload8의 실제 온도 해석은 보류한다.** 시험 조건에서 UART 변화가 없었다는 결과를 남기되 모든 모드에서 무기능이라고 단정하지 않는다. 커스텀 파서에서는 해당 바이트와 프레임 길이·체크섬을 유지하고 실제 온도 표시에는 사용하지 않는다. APK의 날씨 `TemperatureWidget`은 별도 휴대전화 날씨 데이터 경로이며 TEMP 핀의 증거가 아니다.

근거: [TEMP 실험·정적 분석·활용 보류](2026-09-10-temp-input.md). [TEMP 측정 계획](2026-09-10-temp-pin-measurement-plan.md)은 미실행 제안이 포함된 참고 자료다.

## 6. 계기판–Noodoe의 세 커넥터

아래 CN1/2/3은 **사용자의 설명 순서에 붙인 임시 명칭**이다. PCB 실크나 제조사 번호로 확인된 표기는 아니다.

| 커넥터 | 사용자가 관측한 내용 | 현재 분류와 한계 |
|---|---|---|
| CN1: 6핀 | 연결 상태에서 4핀 3.3V. Noodoe 분리 후 계기판 쪽 해당 핀 모두 0V | Noodoe 연결에 의존하는 노드. 전원·풀업 신호·기동 조건 변화 가능성. 네 핀이 같은 레일이거나 Noodoe가 직접 공급한다고 확정하지 않음 |
| CN2: 가로 14핀 | 모든 핀 0V | 측정 당시의 전압만 확인. GND·풀다운 입력·LOW 출력·비활성 신호·미접속 등을 구분하지 못함 |
| CN3: 세로 14핀 | 12V 두 선, 평상시 5V이며 버튼을 누르면 LOW가 되는 세 선, 5V UART | 주 연결부. **버튼 관련 active-low 신호 3개**를 전원 레일 분류에서 수정 |

CN3의 버튼 이름과 각 선의 대응, 풀업을 제공하는 보드, 물리 접점인지 버퍼 출력인지, Noodoe MCU에 직접 이어지는지는 미확정이다. 12V 두 선의 동일 네트 여부·공급 방향·허용 부하도 별도다. 공통 GND는 앞선 실험에서 사용했지만 각 커넥터의 모든 GND 접점 번호가 이 노트에 주어지지는 않았다.

**‘전원과 UART만 존재한다’는 이전 해석은 버튼 신호 발견으로 수정한다. ‘CN2는 전부 0V이므로 기구용/더미’도 아직 가설이다.** 정적 HIGH/LOW만으로 전원·신호·디버그 기능을 분류할 수 없다.

따라서 커넥터에서 SWD를 찾는 우선순위를 낮췄던 판단을 철회한다. CN1이 6핀이라는 이유로 SWD라고 정하지도 않는다. 실제 MCU 식별 뒤 디버그 신호와 접점 사이 연결을 추적해야 한다. 참고로 STM32F429 계열의 리셋 후 SWDIO는 pull-up, SWCLK는 pull-down 상태이므로 디버그 핀도 정적 HIGH/LOW로 보일 수 있다. [ST RM0090 §8.3.1](https://www.st.com.cn/resource/en/reference_manual/rm0090-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

근거: [최신 커넥터 관측과 분류](2026-09-10-noodoe-dash-interconnect.md).

**같은 날 후속 분석:** V5.16에서 전원 상태를 감지하는 MCU 입력을 **PG13, LOW=ON/HIGH=OFF**로 식별했다. CN 접점 번호와 앞단 회로는 아직 미확정이다. MCU STOP 함수는 존재하지만 확인한 OFF 처리에는 별도의 전원 제어 출력·리셋 경로가 있으므로 이를 하나의 ‘슬립 핀’으로 단정하지 않는다. [전원 상태·슬립·종료 분석](2026-09-10-noodoe-power-state-and-sleep.md).

## 7. 부트·업데이트·디버그의 현재 상태

### 7.1 업데이트 수신 경로는 추적했지만 설치 전체는 미완결

```text
순정 APK → Bluetooth Classic SPP
         → 0A 협상 / 0B 제어 / 0D 데이터
         → firmware location ID 0800, file type 2
         → 실행 중 Noodoe 앱의 처리기·이벤트·callback
         → [미확인] 실제 staging / 설치 표식 / resident loader 검증·복사
```

`0800`은 프로토콜 ID이며 플래시 주소가 아니다. 전송 ACK/DONE과 실제 설치·재부팅 성공은 다른 단계다. APK의 `FILE_QUERY`, `BASIC_FIRMWARE_UPGRADE` enum 이름만으로 메모리 읽기나 부트로더 덤프 API가 있다고 볼 수 없다. 검토한 현대식 파서·직렬화기의 해당 분기는 invalid 처리한다.

UART5의 확인된 앱 수신 명령에서는 플래시 읽기·업데이트·부트 명령을 찾지 못했다. 이 차량 UART를 STM32 ROM 부트로더의 USART 경로로 사용할 수 있다고 가정하지 않는다. OTA에 없는 Noodoe resident loader가 UART5를 사용하는지는 미확인이다.

### 7.2 OTA CRC와 미보존 하위 플래시

SR1 계열 OTA의 마지막 4바이트는 STM32 방식 CRC로 재현했다. 파일의 끝 4바이트를 제외하고 little-endian 32비트 word로 읽어 polynomial `04C11DB7`, initial `FFFFFFFF`, 반사·final XOR 없이 처리한다. 네 이미지와 독립 구현 두 개에서 맞았고 전체 residue=0 및 1비트 변형 검출을 확인했다. V5.16의 마지막 word는 `70067874`다.

이 CRC는 APK의 전송 CRC와 구분한다. **CRC를 계산할 수 있다는 사실이 암호학적 서명 검증의 부재나 커스텀 이미지의 부트로더 수락을 증명하지는 않는다.**

| 영역 | 현재 상태 |
|---|---|
| `0x08000000–0x08007FFF` | 최초 부팅·복구 코드 후보. 원본 미확보 |
| `0x08008000–0x0800FFFF` | 앱에 sector 2/3 쓰기 함수가 존재함. 실제 호출 조건·사용 범위 및 코드·설정 경계 미확정, 원본 미확보 |
| `0x08010000–0x0807FFFB` | V5.16 OTA의 매핑 범위. 도너에서 읽어 대조한 덤프는 아님 |
| 도너 내부 플래시 전체 | 실제 용량과 보호 상태 확인 후 보존 필요 |

하위 플래시 함수 `0x080426D4`는 sector 2/3 중 하나의 16KiB를 RAM에 복사·병합하고 지우지만, 분석한 program loop는 앞 **4KiB만 재기록**한다. ‘16KiB 전체 보존 재기록’이라는 설명은 정정했다. 도너에서 실제 데이터 손실이 발생했다고 확인한 것은 아니다.

### 7.3 Noodoe SWD와 계기판 TOOL0는 별도 과제

Noodoe의 SWD 접점은 아직 찾지 못했고 디버거 접속·RDP 판독·내부 플래시 덤프도 수행하지 않았다. 칩이 F429로 식별되면 PA13/SWDIO, PA14/SWCLK부터 실제 패키지와 회로를 대조한다. 코팅으로 접촉하지 못한 것을 단선으로 판정하지 않는다.

원본 보존의 우선 단위는 하위 **64KiB**, 최종 대상은 확인된 용량의 **내부 플래시 전체**다. 기존 디버거로 읽기 조건을 확인하고, 최초 백업은 실행 중 하위 플래시 갱신의 영향을 고려해 코어 정지 조건과 함께 기록한다. **STM32의 RDP1→0 보호 해제는 원본 플래시를 지우므로 백업 방법으로 사용하지 않는다.** [ST RM0090 보호 기능](https://www.st.com/resource/en/reference_manual/rm0090-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

차량 계기판 하네스의 **TOOL0 / RESET**는 Renesas RL78 또는 78K0R 계열의 프로그래밍·디버그 명칭과 맞는 단서다. 정확한 계기판 MCU는 미확정이고 Noodoe SWD와 연결하지 않는다. TOOL0 존재만으로 기존 플래시 전체 읽기가 보장되는 것도 아니다. 이쪽 실물 접속은 아직 수행하지 않았으며 별도 연구로 남긴다. 근거: [TOOL0 조사와 Renesas 1차 자료](2026-09-10-ak550-dash-tool0-reset.md).

상세 근거와 조건부 절차: [펌웨어·업데이트 검증](2026-09-09-ak550-firmware-uart-boot-review.md), [부트로더 백업 계획](2026-09-09-ak550-bootloader-backup-plan.md). 계획 문서의 명령 예시는 실행 완료 기록이 아니다.

## 9. 다음 실험과 완료 기준

새 장비 구매를 전제로 하지 않고, 현재 보유 장비와 원본 보존을 기준으로 순서를 정한다. TEMP는 현재 보류 결정을 유지한다.

| 우선순위 | 다음 작업 | 남길 기록·완료 기준 |
|---|---|---|
| 1 | 커넥터 도면화와 Noodoe MCU 식별 | 보드 양면·CN 관찰 방향·접점 번호, MCU 전체 마킹과 1번 핀 방향. UPPER/LOWER 및 각 버튼과 실제 위치 연결 |
| 2 | 미분류 CN1/CN2와 테스트 패드의 연결 추적 | 전원·USB 분리 상태에서 GND·전원·확인된 MCU 디버그 신호와의 연속성/저항을 기록. 정적 전압만으로 기능 확정하지 않음 |
| 3 | SWD 읽기 조건 확인과 원본 확보 | 실제 디버거 지원·VTref·보호 상태 확인. 허용되는 읽기 경로에서 하위 64KiB와 전체 내부 플래시를 확보하고 반복 읽기·해시 대조 |
| 4 | 연료 표시 2–5칸과 SPEED 대응 확대 | 정상 센더 범위·입력 전기 조건을 확인한 뒤 한 입력씩 변화. 물리 표시·입력 조건·유지 시간·정상 UART를 함께 저장 |
| 5 | 조도 정체 원인 좁히기 | 센서 위치와 동작 조건을 확인하고 A1 캐시 변화·화면 밝기를 대조. 필요 시 원시 센서/이벤트 경로로 내려가 확인 |

각 새 캡처에는 **장치와 펌웨어 식별 수준, 전원 조건, 신호 방향, GND 연결 위치, 바꾼 입력 하나, 실물 표시, 시작·유지 구간**을 짧은 메모로 붙인다. 원본 바이트는 유지하고 정상 프레임·체크섬 실패·미완성 조각을 구분한다. 단계별 핀값을 모르는 곳에는 추정 번호를 채우지 않는다.

현재의 핵심 미완료 항목은 ‘보레이트를 다시 찾기’가 아니라 **Noodoe 내부 플래시의 원본 확보와 실제 커넥터–MCU 연결의 확정**이다.
