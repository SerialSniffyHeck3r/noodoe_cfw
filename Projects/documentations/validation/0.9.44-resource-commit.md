# 0.9.44 — COMMIT resource-proof race

The reported `opcode 67 / result 11`, `Code B / phase 6` decodes to Product COMMIT, UPDATE_COMMIT_AMBIGUOUS and UPDATE_FAILED. Phase 6 here is the Product install view's service state, not a sector number or the Bootstrap metadata writer's diagnostic phase.

## Reproduction and correction

The unchanged 0.9.43 Product updater, UpdateService and BootStore were compiled for Cortex-M and executed with asynchronous resource availability and physical-file I/O substitutes. An immediately queued COMMIT after FINISH starts the separate resource SHA scan, observes it as not ready and returns result 11. There were zero COMMIT erase/program operations. Both O0 and Os reproduced this (496 assertions each; before.json). This demonstrates a software defect matching the reported code, not proof that every result 11 has that cause.

The new Product leaves COMMIT queued while the resource owner is busy. The existing scheduler drains that owner. After completion the original authorization, transaction, image SHA, resource SHA and durable Gate checks still apply. A rejected precondition before any commit write is reported as untouched rejection (12). A failed image/header/journal write or failed durable confirmation remains ambiguous (11); no automatic mutation retry or reset was added.

The Android updater now waits after FINISH for a later Storage processing tick, the exact verified transaction/image and a fresh quiescent observation on the same connection. Waiting is bounded; an epoch change or ambiguous outcome stops it. This fixes the ordering on already-installed Products with observation support. Legacy Storage-owned STATUS is followed by the existing serialized read-only recovery audit. Neither a cached idle snapshot nor an arbitrary sleep authorizes COMMIT. The final write checks remain on the device.

After a failed COMMIT and device restart, an old attempt can be archived as PRODUCT_NOT_COMMITTED only when the same UID is confirmed, the stable Gate journal is confirmed with no candidate, the updater is fresh IDLE with zero transaction/received/verified bytes, and resident pending CRC is zero. A live failed/ambiguous runtime, armed candidate, trial, resource/FAT work or uncertain RESET remains protected. Records are archived rather than deleted. Every subsequent update still runs its ordinary recovery preflight.

## Verification

- Android: 61 tests, no failures/skips; lint has no Error/Fatal. Real NdcpSession and journal tests exercise the single COMMIT/RESET sequence, legacy audit, rejected writes, epoch changes, stuck snapshots and no-candidate reconciliation.
- Actual ARM Product/BootStore/UpdateService: 108 runs, 13584 assertions, O0/Os. New cases cover delayed resource proof, connection replacement during the wait, missing resources, and existing interrupted commit/readback tests.
- Product Debug and Release builds and memory gates pass. No compiler policy, heap, stack, queue, partition or RAM reservation changed.
- APK versionCode 84 / 0.9.44 has the same signer. APK riding contract matches the packaged Product SHA `c8c6a554525d830c87ac5d78c15acca0a1db032af2645acdb6b06ec0afe56cec`.
- Gate, Bootstrap, stock, uninstaller, diagnostic and resource binaries are byte-identical to 0.9.43. No new UI/font/map/radio initialization changes or new screenshots are claimed.

## What remains unverified

No physical Noodoe, NOR, RF link, Galaxy phone or actual installation was exercised. The async resource provider and physical I/O are controlled test substitutes; production updater/boot policies run as ARM code. No latest log was supplied for this particular report at publication. A real NOR failure can also yield result 11. Keep diagnostics and do not treat this result alone as proof of untouched storage. Current-device recovery and a successful future installation require the device's actual journal/state checks.
