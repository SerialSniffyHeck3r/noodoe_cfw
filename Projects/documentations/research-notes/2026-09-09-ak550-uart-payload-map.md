# AK550용 Noodoe: 계기판 ↔ Noodoe UART에 실리는 정보

2026-09-09. **순정 펌웨어 BIN의 수신·송신·소비 코드를 근거로 한 분석.** APK의 클래스/필드 이름을 펌웨어에서 확인된 의미로 취급하지 않았다. 실물 UART 캡처와 장치 쓰기는 하지 않았다.

> **2026-09-10 실물 대조:** 사용자가 제공한 Agilent `PRINT_01.CSV`에서 `F5 A1 02 01 07 50`을 115200/8N1로 복원하고 XOR를 확인했다. 이 문서의 Noodoe→계기판 A1 조도 단계 송신과 일치한다. [파형 검증 보고서](2026-09-10-agilent-scope-uart-decode.md). 아래의 다른 명령·필드까지 실물 검증됐다는 의미는 아니다.

> **2026-09-10 양방향 추가 검증:** Arduino GND를 계기판 GND에 직접 연결한 뒤 UPPERPIN에서 정상 A1 30개, LOWERPIN에서 정상 21 116개를 확보했다. 21 payload +4..7의 `7B 8E 00 00`은 **36,475km**이며 사용자가 실제 계기판 ODO와 일치함을 확인했다. 기능상 UPPER=Noodoe TX, LOWER=계기판 TX로 구분할 근거를 확보했으며, 공식 커넥터 번호·관찰 방향은 여전히 별도 기록이 필요하다. [양방향 캡처 보고서](2026-09-10-upper-lower-uart-confirmed.md).

## 결론

> **2026-09-10 연결부 상세 관측:** 사용자는 6핀 CN, 가로 14핀 CN, 세로 14핀 CN을 구분했다. 세로 CN에는 12V 두 선과 **버튼을 누르면 5V→LOW가 되는 세 선**, 5V UART가 있다. 이에 따라 전원과 UART 외 신호선이 없다는 이전 분류를 수정했다. 6핀 CN의 3.3V 노드와 가로 CN의 0V 핀은 전원/더미로 확정하지 않는다. [최신 연결부 구성과 연구 반영](2026-09-10-noodoe-dash-interconnect.md).

> **2026-09-10 연료 0칸·1칸 실측:** FROMDASH-GAS1의 1칸 상태는 정상 33개 모두 payload **3=51**, lower-fuel0의 0칸 상태는 정상 23개 모두 **3=50**이었다. **하위 니블 1·0이 실제 표시 1칸·0칸에 대응**하며 상위 5는 유지됐다. 총 5칸 표현은 유력하나 상위 니블 의미와 2~5칸은 미검증이다. 두 파일 모두 payload **2=00 유지**이므로, 아래 payload 2의 공용 잔량 위젯 소비 경로를 AK550 실물 연료 필드와 동일시하지 않는다. [두 캡처 비교](2026-09-10-fromdash-gas1.md).

계기판에서 Noodoe로 들어오는 경로에는 **속도, 적산거리(ODO), 잔량 게이지 값, 온도형 값, 아직 의미를 모르는 상태값**이 있다. 별도로 250바이트와 71바이트 레코드를 받아 휴대전화 통신으로 넘기는 경로가 있다.

Noodoe에서 계기판으로 나가는 쪽은 **자체 조도센서로 계산한 0..9 단계값**, 그리고 **통신 재초기화/재요청 및 종료와 연결된 명령**을 확인했다. 기존 문서의 “네 버튼 비트”라는 설명에는 근거가 부족했다.

이것은 아래 V5.16 이미지에 구현된 경로이다. 사용자가 구입한 2017 AK550 모듈의 현재 탑재 버전이나, 실물에서 모든 명령이 사용되는지를 확인한 결과는 아니다. 특히 공통 이미지에 0x41/0x42 처리기가 있다는 이유만으로 AK550이 두 종류를 모두 송신한다고 단정하지 않는다.

## 대상과 전송 형식

- SHA-256: `3b64673054ca84b9cf504f4cc7ebcb2e6615b9fbf59df79a37a92dcf14f037ca`
- 크기: 458,748바이트. 코드 기준 주소: `0x08010000`.
- UART5, 115200 baud, 8N1, 흐름 제어 없음. GPIO 설정은 PC12 TX / PD2 RX, AF8 경로. **MCU 포트명이며, 미확인인 계기판↔Noodoe 커넥터의 핀 번호가 아니다.**
- DMA 설정이 존재하나, 앞선 원시 코드 감사에서 연결이 확인된 수신 경로는 한 바이트씩 IRQ 수신하는 경로다.

```text
F5 | CMD | LEN | PAYLOAD[LEN] | XOR
```

아래 정상 길이의 프레임에서 체크섬은 `F5`부터 마지막 payload까지 바이트 XOR이다. 수신 상태기계는 `0x0804EA14`, 체크섬 함수는 `0x0804EBB0`, 송신 프레임 생성은 `0x0804E9AE`에 있다.

| 방향 | CMD | 소비/생성하는 payload 크기 | 펌웨어로 확인한 내용 |
|---|---|---:|---|
| 계기판 → Noodoe | `21` | 9바이트 | 기본 차량 상태 |
| 계기판 → Noodoe | `22` | 11바이트 | 기본 상태 + 의미 미확인 16비트 값 |
| 계기판 → Noodoe | `41` | 250바이트 | RAM에 보관한 뒤 SPP `16` 응답으로 전달하는 레코드 |
| 계기판 → Noodoe | `42` | 71바이트 | 이벤트로 넘겨 SPP `C6`으로 전달하는 레코드 |
| Noodoe → 계기판 | `01` | 1바이트 | 확인한 상위 경로: 재요청 시 `04`, 종료 시 `00` |

## 21/22: 차량 상태의 바이트별 의미

아래 offset은 프레임 전체가 아니라 **payload 첫 바이트를 0으로 센 값**이다. 분해 함수는 `0x0804E920`, 내부 상태 저장은 `0x080330F0`이다.

| Payload offset | 실제 연산 | 의미와 확실성 |
|---|---|---|
| `0` | unsigned 8비트 | **현재 속도, 기본 정수 km/h: 강한 근거.** `kmh.png`/`mph.png` 선택과 숫자 변환이 연결된다. 값 5로 정지/주행 상태를 가르고, 최고값을 추적하며 속도 게이지에 사용한다. |
| `1` | unsigned 8비트 | **미확인.** 내부 구조체 +7, UI RAM `0x200232B1`로 복사한다. |
| `2` | unsigned 8비트 | **잔량 게이지 입력: 확정된 소비 경로.** 0, 1..20, 21..40, 41..60, 61..80, 81 이상을 0..5 단계로 나눈다. 위젯명은 `BatteryWidget`, 그림명은 `fuel_battery` 공용이다. AK550의 연료량이라는 해석은 차량 맥락상 후보이며, 물리적으로 정확한 연료 %나 최대값 100을 보장하지 않는다. |
| `3` 하위 4비트 | `value & 0x0F` | **AK550 연료 표시 칸 수 후보.** 후속 실측에서 0칸→0, 1칸→1 대응 확인. 2~5칸은 미검증. |
| `3` 상위 4비트 | `value >> 4` | **총 칸 수 후보.** 후속 0칸·1칸 캡처 모두 5. 실물 총 5칸과 맞지만 의미 미확정. |
| `4..7` | little-endian unsigned 32비트 | **적산거리(ODO): 강한 근거.** 펌웨어가 직접 `OdometerWidget`으로 선택한 화면에서 6자리 정수로 표시한다. 기본 km, 설정에 따라 약 1.609로 나누는 변환 경로가 있다. 실제 차량의 값 증가와 원천 저장장소는 실측하지 않았다. |
| `8` | unsigned raw에서 40을 빼서 16비트로 저장 | **온도형 값 후보, 현재 활용 보류.** 연산은 확정. 사용자는 TEMP 전압을 바꿔도 UART가 변하지 않았다고 보고했다. TEMP 핀과의 연동·센서 정체·물리 단위는 미확인. 바이트 위치와 프레임 처리는 유지한다. [관측 및 보류 결정](2026-09-10-temp-input.md). |
| `9..10` | little-endian unsigned 16비트 | **22 전용 추가값, 의미 미확인.** |

주요 소비 경로:

```text
UART payload → 0804E920 분해
             → 080330F0 → RAM 20022F50 (16바이트 내부 상태)
             → 08032E9E getter
                ├─0801BD82: 거리/속도 게이지 표시
                └─0801CC88: UI 값 갱신, 6단계 게이지 변환
```

구조체 배치는 `+0=u32 거리`, `+4=16비트 raw-40 온도형 후보`, `+6=속도`, `+7=미확인`, `+8=연료형`, `+9/+10=니블`, `+12=u16 확장값`이다. 나머지는 패딩/미정 영역이다. `21` 분해 경로는 +12 확장값을 초기화하지 않으므로 `21`에서 추가값이 항상 0이라고 해석하면 안 된다.

`0801CCC2/CCD6/CCEA/CCFE`는 각각 81/61/41/21을 비교한다. 거리 UI 경로 `0801CD5A →0801CC40`은 설정에 따라 `0x3FCDF3B6`(float 약 1.609)로 나눈다. 속도 단위 선택에는 `kmh.png`/`mph.png` 자산명이 사용된다. `OdometerWidget` 문자열 `08076448`을 인식하면 위젯 선택값 1을 저장하고, `080121BC..121C6`에서 거리 표시 함수 `08011DCC`를 호출한다. 잔량은 `BatteryWidget`과 `img_widget_fuel_battery_0/20/40/60/80/100.png` 자산에 연결된다. 따라서 잔량 게이지의 존재와 그것이 AK550의 연료 퍼센트라는 해석은 구분한다. 초기 화면에는 getter에서 받은 raw 거리를 직접 표시하는 호출도 있으므로, 모든 화면·시점이 단위 변환된 캐시를 통과한다는 뜻은 아니다.

## UART에서 받은 값과 Noodoe가 계산한 값의 구분

**정지/주행 여부, 최고 속도, 정지 시간은 기본 UART payload에 별도 필드로 실리는 것이 아니라 Noodoe가 속도값으로 계산한다.**

- `0803313C`의 속도 `<5`에서 시간 기준을 잡는다.
- 속도 `>=5`로 바뀌면 `08033162..3318A`에서 `(현재 tick-시작 tick+500)/1000`을 16비트 카운터에 더하고 기준을 지운다.
- `08032F52` 조회는 진행 중인 구간의 `(현재 tick-시작 tick)/1000`도 더한다. 값을 돌려준 뒤 구간 카운터를 초기화한다.
- 따라서 기존 문서의 `riding_seconds`, “speed>=5 동안 누적”은 잘못된 설명이다. **속도 5 미만 구간을 누적하는 정지 시간 성격의 값**이다. 초 단위 의도의 `/1000` 연산은 확인했으며 물리 시간을 캡처한 것은 아니다.
- `080331CC..331DC`는 수신 속도의 최고값을 유지한다.
- 5를 넘나드는 전환은 이벤트 3/4로 만들어지고 `08031110`에서 휴대전화 쪽 SPP `C2`, 값 `1/0`으로 이어진다(연결 조건 검사 있음). 이것은 차량 UART의 CMD가 아니다.
- 파생 요약 getter의 9바이트는 `상태 1 + 거리 4 + 정지시간 2 + 최고속도 1 + 현재속도 1`이다. 상태 첫 바이트는 상위 응답 작성 과정에서 별도 함수값으로 교체된다.

## 41/42: 무엇이 들어 있는지 어디까지 아는가

`41`은 250바이트를 `0x20021A40`에 보관한다. 휴대전화 SPP `16` serializer `0x08029EEA`는 `16 + 1 + 99 + 99 + 35`바이트로 나누어 복사하고 앞에 16비트 결과값을 붙인다. **블록 경계는 드러나지만 각 블록의 이름/단위는 이 경로에서 해석하지 않는다.**

`42`는 71바이트를 `0x200227D4`에 보관하고 이벤트 5를 만든다. 대응 소비자와 serializer는 SPP `C6`으로 71바이트를 그대로 넘긴다. 송신 큐 등록 성공 시 소스 버퍼를 지운다. 이는 휴대전화 수신 확인과 같지 않다. 이벤트 큐에 등록하는 경로와 대응 소비자 모두 확인했으나, 큐 dispatch의 전체 간접 호출 연결은 이번 블록 감사에서 재생성하지 않았다.

APK에 battery/Ionex라는 이름이 있어도, 펌웨어만으로 이 71바이트를 **AK550 시동 배터리 전압**이라고 부를 수 없다. RPM·TPMS·전압·브레이크/방향지시등 비트의 위치도 이번 분석에서 확정하지 못했다.

또한 250바이트 캐시는 처음 0으로 초기화된다. 기존 휴대전화 조회에서 전부 0이 나왔다는 관찰은, 차량 UART에서 0인 레코드를 실제 보냈다는 증거가 아니다. 아직 채워지지 않은 캐시를 읽었을 가능성도 있다.

## Noodoe → 계기판: 밝기 단계와 통신 재요청

### A1: 자체 조도센서로 계산한 단계

```text
센서 결과 레지스터 읽기 (0804E3A2)
 → 측정값 정수변환 (08033354)
 → 임계값 10개로 분류 (0802036E/08020518)
 → 단계 저장 (200232FC →20023308)
 → A1 payload {01, 단계} (0804E8FC)
 → UART5 송신
```

정상 갱신 경로의 단계는 0..9다. 원시 lux나 백라이트 퍼센트가 아니다. 같은 단계로 Noodoe 자신의 백라이트 목표 10/20/…/100을 계산하는 별도 경로도 있다. 상대 계기판이 수신값을 실제로 어떻게 사용하는지는 상대 펌웨어가 없어 미확인이다.

**단계 경계값은 `0x0800C040..0x0800C067`의 40바이트에서 읽는다.** 이는 이 OTA BIN 시작주소보다 아래다. 실물 하위 플래시 덤프 없이 단계별 조도 경계값과 인덱스 순서를 확정할 수 없다.

이 경로의 핵심 간접 호출은 압축된 초기화데이터를 원본 알고리즘으로 복원하여 연결했다. 1,823바이트 압축입력으로 3,597바이트 초기 RAM 데이터를 복원했으며, `0x20000C5C`의 F5 함수 테이블과 `0x20000C00`의 UART5 테이블을 확인했다. 복원 파일은 실물 RAM/부트로더 덤프가 아니다.

### 01: 통신 복구와 연결된 요청

`0804E8C0`은 인수 하나 1..4를 `01/02/04/08` 중 하나로 바꾼다. 네 개의 독립 버튼을 OR한 코드가 아니다. 확인한 상위 경로는 인수 3→payload `04`와 종료 경로 인수 0→payload `00`이다.

```text
F5 01 01 04 F1       # 통신 재초기화/재요청 경로
F5 01 01 00 F5       # 링크 종료 경로
F5 A1 02 01 00 57    # 조도 단계 0
F5 A1 02 01 09 5E    # 조도 단계 9
```

위는 생성 함수와 XOR로 계산한 예이며 실측 캡처가 아니다. `01=04`를 상대 계기판이 정확히 어떤 명령명으로 취급하는지는 미확인이다.

송신은 수신 상태기계와 연결된다. 초기 3000 tick 타이머 이후 재요청 경로가 있고, 재초기화 후에는 400 tick 감시 상태가 된다. 이 상태에서 **유효 수신 프레임 네 개마다 최신 조도 단계를 A1으로 회신**한다. 400 tick 동안 입력이 없으면 800 tick 대기로 바꾸고, 다시 만료되면 재요청 경로로 돌아간다. 따라서 A1을 고정된 몇 Hz 송신이라고 단정하면 안 된다. 실제 시간 주기는 캡처하지 않았다.
