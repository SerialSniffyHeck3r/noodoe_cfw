# Reserved SDRAM diagnostic

This module is prepared but **not wired into Runtime or tested on hardware**.
It does not change `g_bsp_ram.ready`, its basic result, or measured capacity.
No code calls `BSP_RAM_Init` again. The existing allocator reserves one private
4 MiB arena by default, leaving prior client allocations and the original64KiB
bring-up scratch outside every requested test address. The arena is never freed.

One owner task calls `BSP_RAMTest_Prepare(0)` after successful basic RAM init,
then `BSP_RAMTest_Service(256)` approximately every2ms. A UI or debug host can
request a test through the mailbox; the owning task alone consumes it. Direct
`Start(operation_id, seed)` and `Cancel(operation_id)` are also available to that
owner. Neither waits for completion. `GetDiagnostics` returns the last published
snapshot without spinning on a lower-priority task.

The CPU test writes/reads walking-one and walking-zero values at4KiB intervals.
Eight full-arena passes use address-derived values, their complement, alternating
bits, zero, ones, and a deterministic mixed-address pattern/complement. A complete
fill precedes each verification sweep so aliased locations cannot pass merely
because each was immediately read back. Next,512-byte chunks travel from an
internal buffer to SDRAM and back using DMA; both SDRAM and the returned buffer
are compared against the immutable expected data.

DMA2 Stream0 has no other compiled ongoing owner: its other use is the one-time
`BSP_RAM_Init` transfer. The port checks that initialization completed, the handle
is ready/unlocked, EN and IRQ bits are clear, and direction/increments/data sizes
match the generated byte-wide normal memory-to-memory configuration. It does not
reinitialize or steal a busy stream. `HAL_DMA_PollForTransfer(...,0)` is called
only after hardware TC and EN=0 are observed, avoiding HAL's premature-ready
timeout behavior. DMA error/100ms timeout/cancel enters a nonblocking disable
phase. A stream that will not disable within another100ms is quarantined for the
rest of this boot; buffers and arena are not reused.

Two512-byte static buffers consume1KiB internal SRAM, plus small state records.
At256 word operations and2ms service intervals, eight CPU sweeps of4MiB need
about131seconds of scheduling slots; walking/DMA add approximately one minute.
Actual duration depends on caller scheduling and DMA completion. No measured
device timing or30 FPS preservation is claimed yet. `max_slice_cycles` records
DWT cycles for the work before diagnostic publication, including any preemption
during that interval. It excludes the final short critical-section publication.
The counter is enabled without resetting the shared DWT epoch. Root should
measure this value and actual display progress before increasing the budget.

`g_bsp_ramtest_command` fields are version, command, operation_id, seed,
request_seq. Write the request body first, then a new increasing sequence as its
commit word; wait for request_ack before modifying that body again. START=1,
CANCEL=2; unknown command/version returns INVALID. Cancellation must name the
current operation. Duplicate/stale commit sequences are ignored. Use a new
nonzero operation ID for each run. request_ack/request_result report acceptance;
completed_request/completed_operation identify the START operation that ended.
The terminal state distinguishes PASSED, FAILED and CANCELLED. SWD readers use
the diagnostic sequence before and after the record and accept only equal even
values. This is not an arbitrary physical-memory write mailbox.

All software-issued addresses are confined to the reserved arena. As with any
live test, a physically faulty address decoder could alias a requested address
elsewhere; software confinement cannot promise preservation under that hardware
failure. The prior basic test's capacity/address-line checks remain the initial
gate. This additional4MiB pass does not establish every cell of64MiB or certify
temperature/voltage retention corners.

Offline validation: the real CPU state machine was compiled for Cortex-M4 and
run under Unicorn at `-O0` and `-Os`,77 assertions each. The nine scenarios cover
allocation/idempotence, successful bounded full test, guard regions, walking-bit
fault, address alias, invalid/stale mailbox commands, DMA corruption, timeout,
delayed cancellation and stuck-DMA quarantine. DMA/RTOS/memory fault behaviors
are mocks; these tests do not validate silicon timing. The production DMA port
also compiled separately against the actual project HAL/CMSIS/FreeRTOS headers
with `-Wall -Wextra -Werror`. No whole-project build, flashing or Runtime edits
were performed by this module's implementation task.
