# 0.9.55 display maps and reset handoff

This release addresses the four reported problems using 0.9.44 as the baseline. The fixes run in Product and the matching Android companion. Hardware LCD timing, ignition behavior and Bluetooth installation remain unmeasured; the evidence below is software execution, including compiled Cortex-M firmware paths.

## Installation restart

Product checked the saved Bluetooth key generation before closing the controller. A final key callback during controller shutdown could change that generation afterward. The final IRQ-protected reset check then refused reset after the updater had entered COMMITTED, leaving the update paused. A new test using the unchanged 0.9.44 adapter reproduces this path.

0.9.55 closes the controller first, then drains settings/config storage until the exact final key generation is durable. It remains in RESET_WAIT during that drain. The existing acknowledged reply, 1.5-second handoff, committed-image proof, ten-second bond-save timeout and final interrupt-protected check remain. A real storage failure still stops the update. The test covers late shutdown callbacks and save failures, with 28 assertions each at O0 and Os; the existing Product/BootStore suite passes 108 runs and 13584 assertions.

The updater performing the FIRST installation of 0.9.55 still belongs to the currently running older firmware. This Product fix applies after 0.9.55 has booted; it cannot retroactively replace an already executing 0.9.44 reset path. Save diagnostics and follow the existing recovery procedure if that initial upgrade pauses.

## Continuous roads

The old Android compiler split chains into twelve-point fragments and selected at most sixteen roads / forty-eight road points per tile. A connected sixteen-piece, sixty-four-point example lost middle pieces. The new compiler selects complete roads using projected physical width (minimum0.35 source pixels), preserves junctions/endpoints, merges compatible chains, and simplifies their geometry with1.25px tolerance. It does not delete selected road fragments to meet a point quota. Narrower roads may disappear as a whole at small scales.

NVM5 carries a complete512px tile, up to48KiB /4096 features /10000 points, negotiated by A8 flags bit16. These are packet validation limits: an oversized tile fails as a whole, leaving the last complete cache intact. Optional terrain stays separately bounded and cannot displace roads. Eight tiles, immutable snapshots, four-tile selection and raster scratch use SDRAM. NVM1/NVM4 remain separately validated. The new APK and Product must match.

Twenty-eight Korea-map samples at four locations and seven scales fit the new packet format. The actual ARM receiver retained every emitted feature/point in all28, rejected all28 deliberately malformed packets without replacing the prior tile, and rasterized the densest sample. The render harness used 3,388,960 bytes of named SDRAM allocations; this is the harness workload, not the whole firmware's peak.

## Hidden maps and changing screens

Map work is admitted only when the map is actually visible. Leaving the map, ignition-off, settings, large warnings and phone popups stop raster work. Android polls visibility at200ms and cancels an incomplete RAM-only map upload; already accepted work drains through its existing owner. A new owner test performed100 hidden-page calls with zero additional map uploads.

Input, ignition and warning policy still run on their5ms owner ticks. Expensive UI model, label and scene composition runs only when the graphics30Hz deadline is due. The cadence tests admit30 compositions over200 five-millisecond ticks, including3ms of intervening work. A one-shot render deferral prevents a deadline crossed after composition was skipped from consuming a stale frame; normal power-only rendering remains independent. Map work retains an eight-row / cooperative2ms slice; fixed-clock and advancing-clock tests produce identical pixels. A single row is the preemption boundary, so this does not prove a physical2ms worst case on all maps.

Every completed EVE display list remains fully validated. The former per-frame state compaction and RAM_DL rewrite are removed. The list is read once through bounded SPI exchanges under one chip-select interval. Actual coprocessor completion,8KiB limit, physical-swap retirement and texture leases remain. The baseline21MHz runtime SPI clock and Bluetooth startup probing are unchanged. Earlier pre-map0.9 code used the same runtime SPI rate; a radio-speed change is not established as the cause of the steady-state display load.

## Large fuel warning

The veil task now owns the full480x480 shell even during ignition scene clipping. It multiplies destination RGB by20/255 while preserving the alpha channel used by rounded warning drawing, with scoped EVE clip/stencil/blend state. The original low/critical icon and warning conditions remain.

Six actual LVGL/EVE frames cover low and critical warnings while riding, during welcome and after parked return. Eighteen injected predecessor-state cases produce identical pixels; measured background RGB gain is below0.10 outside the icon. The original veil also worked in a controlled baseline simulation, so the precise physical cause of the reported intermittent failure is not conclusively reproduced.
