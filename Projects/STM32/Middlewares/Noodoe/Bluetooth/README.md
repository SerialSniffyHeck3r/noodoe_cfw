# Bluetooth Classic SPP bring-up

This service is a project-owned port of unmodified BTstack commit
`431d58d5613fd8fae38afe50282b25302de84bf7` from
https://github.com/bluekitchen/btstack . BTstack's original personal/noncommercial
license remains in the vendor tree; distribution must comply with that license; zero price alone is not a commercial license. No
MFi, iAP, BLE, audio profile or OpenNoodoe source is included in this module.
`module.build.json` explicitly lists compiled vendor sources. Do not compile
the entire upstream example/platform/codec tree.

## Initialization and controller identity

After Cube GPIO/DMA/USART1 setup call `Bluetooth_Start()` once from task context.
The one statically allocated task runs at FreeRTOS priority32, above the normal
UI24. It uses an8KiB static stack and separate bounded RX2KiB/TX1KiB queues per
single inbound PHONE role. `Bluetooth_SetPairingWindow(120)` enables initial PC pairing;
discoverability otherwise stays off. APIs are declared in `NoodoeBluetooth.h`:
the name avoids Windows' case-insensitive collision with upstream `bluetooth.h`.

Stock sequence: PA8 LOW, PI1 HIGH, UART115200 8N1 RTS/CTS, arm RX DMA, delay10ms,
PA8 HIGH, delay150ms. H4's first receive completes this sequence before its
open returns; both delays yield to other RTOS tasks. `communications-audit.md`
supplies the binary evidence. The GPIO
sequence is verified statically; physical net labels are still unconfirmed.

BTstack sends HCI Reset and Read Local Version before vendor commands. Only
TI manufacturer13 plus LMP subversion `0x1B90` (CC256xB ROM) or `0x9A1A`
(CC256xC ROM) selects a script. Unknown identity immediately shuts BT down with
diagnostic0x301, without downloading a guessed patch. A20s startup deadline
produces0x302. Any failed initialization command shuts down and preserves the
controller status. Hardware-radio success is distinct from compilation.

Both pinned TI Classic-only script assets are included (B9,243bytes, C6,760bytes).
They were generated by the pinned upstream converter from service packs
[CC256xB1.8](https://bluekitchen-gmbh.com/files/ti/service-packs/cc256xb_bt_sp_v1.8.zip)
and [CC256xC1.5](https://bluekitchen-gmbh.com/files/ti/service-packs/cc256xc_bt_sp_v1.5.zip),
the upstream-maintained TI mirror. Original BTS archives, TI licenses and hashes
are in `patches/manifest.json`. No BLE/AVPR add-on is selected. Runtime LMP
matching is mandatory, even though both assets are available.

Default target baud is921600; `BLUETOOTH_MAIN_BAUD=3686400` selects the stock high
rate only for a subsequent measured throughput test. Pinned BTstack's
`ENABLE_CC256X_BAUDRATE_CHANGE_FLOWCONTROL_BUG_WORKAROUND` toggles host CTSE for
the TI FF36 baud command. RTS remains active. eHCILL is explicitly disabled by
the chipset script adapter; no sleep/wake behavior has been proven yet.

## DMA and Cube callback integration

Forward shared HAL RX/TX/error callbacks to `BSP_BT_HCI_OnRxComplete`,
`BSP_BT_HCI_OnTxComplete`, `BSP_BT_HCI_OnError`. USART1 IRQ forwards to
`HAL_UART_IRQHandler(&huart1)` at priority5; RX DMA2S5 and TX DMA2S7 use priority5
and Normal mode. TX DMA alone is insufficient: STM32 HAL completes TX in the
USART TC interrupt. BSP enables that IRQ but the root owns the vector handler.

RX uses a small BSP-owned DMA arm sequence instead of editing the vendor HAL.
`HAL_UART_Receive_DMA` always reads SR/DR to clear ORE; this discards a valid
byte already received between H4 blocks. The BSP holds PA12 RTS HIGH in the
DMA completion ISR, preserves any in-flight byte in DR, arms the next normal
DMA, then restores AF7 RTS. The DMA enable/RTS release pair is critical so a
one-byte immediate completion cannot release RTS after its completion ISR.
Preexisting framing/noise/overrun flags become errors, never silently accepted.
Callbacks set event bits and wake the BT run loop; no protocol, storage or LVGL
work runs in the IRQ. Buffers must reside in DMA-visible SRAM and remain live.
The project port captures the BT task at Open and initializes FreeRTOS's
`higher_priority_task_woken` output before every notification. This corrects
the pinned upstream helper's uninitialized variable without modifying vendor
files. Close detaches the callback and clears that owner.

`Bluetooth_QuiesceTransport(timeout_ms,&token)` is the bounded storage-worker
exception to the ordinary nonblocking API. Its atomic mailbox is handled only
by the BT owner, which holds host RTS HIGH, keeps it HIGH across RX DMA rearms,
and drains in-flight bytes with IRQs still enabled. Acknowledgement requires
at least2ms settling, idle TX/TC and no pending/error UART byte. H4's one
outstanding transmit block is retained until resume. Failure cancels its
token and must stop metadata commit before erase. On every path after success,
`Bluetooth_ResumeTransport(token)` waits at most100ms for the owner to resume.
No storage callback directly manipulates HCI registers. These checks are
tested in an ARM model; controller flow-control timing still needs hardware
validation once HCI communication is available.

## Upper APIs and ownership

- `Start/Stop/Discover/Pair/Forget/Connect/Disconnect` enqueue copied requests.
  Return0 means accepted, not that an asynchronous connection has completed.
  Inspect `GetLinkState` and diagnostics. There are8 request slots.
- PHONE and PHONE2 accept independent inbound RFCOMM channel1 sessions; only ELM initiates connections. Channel0
  performs SPP SDP lookup. One singleton SDP query is serialized across roles.
  A single remote address cannot occupy multiple roles. Failed outbound links
  retry after5s; explicit Disconnect cancels retry.
- `Send` copies a whole block or returns QUEUE_FULL. `Receive` copies available
  bytes, returning0 for empty. No wire message boundaries are promised by SPP.
  Connection boundaries discard old session queues.
- `SendSession/ReceiveSession` additionally take a previous `Bluetooth_LinkState`
  snapshot. UP state, CID, address and reconnect counter are rechecked under
  the same queue critical section. A changed session returns NOT_READY without
  enqueuing, consuming RX bytes or changing caller output. Protocol consumers
  should use these APIs so a higher-priority BT task cannot move a transfer
  into a replacement connection between snapshot and queue access.
- Link/controller snapshots (`GetLinkState`, `GetDiagnostics`, `GetControl`)
  and session-bound transfers currently support thread-mode consumers strictly
  below the BT owner's FreeRTOS priority32, with interrupts enabled. This is
  the current UI24, I/O25 and lower-priority Storage worker arrangement; ISR
  readers and consumers at priority32 or above are outside this contract.
  The reader's critical section prevents BT from interrupting its copy, but
  the owner does not publish every multi-field state update atomically. A
  higher-priority reader could interrupt that publication and observe a mixed
  state. Supporting such readers requires a separate atomic-publication change;
  these APIs are not unconditionally thread-safe at arbitrary priorities.
- Each RFCOMM connection grants one receive credit at a time, only when its
  buffer can accommodate the negotiated MTU. A stalled consumer therefore
  stops its own sender without blocking other roles. Overflow is counted and
  that channel disconnected. TX queue removal occurs only after successful send.
- Pairing window permits SSP Just Works. Legacy PINs are never guessed: use
  `Pair(address,"1234")` or the actual device PIN. PINs are limited to16bytes.
  Six RAM link keys have copy-in/copy-out storage APIs. `ImportKeys` is allowed
  before first start. `ExportKeys` and `MarkKeysPersisted(generation)` let a
  storage worker write NOR outside BT callbacks; an old save never clears a
  newer update. No internal flash sector is used for this DB.

`g_bluetooth` (magic42545331/version1) and `g_bsp_bt_hci` (42484831/version1) are
SWD diagnostics. Keys and PINs are deliberately absent from those diagnostics.

## Tests and PC tools

`tools/tests/bt_transport_host/run.py` executes production ARM C atO0/Os in
Unicorn: queue wrap/role isolation, full-buffer rejection, send failure retaining
data, RX overflow, request copies, both patch identities and script boundaries,
key eviction/export/generation, DMA handoff and fault paths, including RX/RTS
readiness before reset release, exact 10/150 ms ordering and PHONE session
epochs across a reconnect between application polls, and initialized ISR
notifications with/without a higher-priority task wake, quiesce token ownership,
settling, RX-rearm pause preservation, deferred TX, busy/error refusal and
timeout cleanup, and session-bound queue transfers with simulated BT preemption
immediately before lock entry (CID/address/epoch/state changes). The current
suite has551 assertions per configuration, including the isolated Reset
diagnostic described below. MMIO read hooks confirm the pending UART DR byte is never
discarded by a CPU read. These tests mock radio and RTOS scheduling, so they do
not certify multi-radio connectivity or baud signal integrity.

`tools/tests/bt_transport_host/test_pc.py` has8 no-radio tests for Windows SDK ABI,
partial sends, timeout/error handling, SDP registration lifetime, explicit
authentication target/numeric-comparison bounds and NMEA/ELM simulator output.

`tools/bluetooth_pc.py` is a no-GUI Windows WinSock/Bluetooth API CLI. Run help for
discover/pair/exchange/serve. `BluetoothSocket` is importable by the OTA CLI.
Servers register an actual SPP SDP record with WSASetServiceW. NMEA/ELM output is
synthetic test data. `serve --duration` bounds a connected session; listening
ends with Ctrl+C. Documented blind legacy-PIN pairing never invokes a wizard;
SSP exchange registers an explicit remote authentication callback. Just Works
acceptance requires remote no-input/no-output; a displayed numeric comparison
needs an explicit matching `--confirm` value. This tool does not silently pair
unrelated discovered devices.

## Isolated fixed Reset diagnostic

`Bluetooth_RequestResetDiagnostic(sequence)` publishes command2 through the
existing48-byte control mailbox. `Bluetooth_RequestStart` remains command1.
Publication and queue acceptance are separate from completion. Only the BT
owner executes command2, while service OFF/FAULT, underlying HCI OFF and the
H4 transport fully detached. Conflicting queued/new START, STOP and other
commands are rejected while raw ownership is active. No automatic retry,
Read Version, chipset patch, arbitrary HCI command or SPP operation is run.

The BSP follows the normal PA8/PI1 and RX-before-reset startup sequence. It
temporarily clears only USART CTSE, submits the constant `01 03 0C 00` once,
and requires TX NDTR0 plus USART TC within20ms. It restores CTSE immediately
after that transfer and observes raw Normal-DMA RX for at most500ms from
submission. The existing reset settling adds10+150ms; RTOS delays yield during
both intervals. Cleanup restores CTSE on failure paths and closes the known
transport/power lifecycle. A failed DMA abort quarantines the static buffers
and prevents further startup. It is a volatile controller Reset experiment,
not firmware/NVM programming or proof that the whole Bluetooth stack is ready.

`Bluetooth_GetResetDiagnosticSnapshot(&record)` copies the separate192-byte
`BSP_BT_ResetDiagnostic` record without accessing hardware or waiting. Return1
means a stable snapshot is available, including the initial phase0 record;
it does **not** mean a diagnostic has completed. Match operation_id and
request_sequence to the accepted control token, require control phase3/4 and
matching completion_sequence, and raw phase6. The controller remains OFF/FAULT
even when the raw test succeeds. The header defines byte layout and results.

Raw data is copied only after successful DMA stop. `data_valid=0` on abort
failure means the bytes are not a coherent result. `tx_submit_count=1` records
one software call; `tx_completed_bytes=4` additionally requires NDTR0/TC.
CTSE before/bypass/restored values and `flow_restore=1` prove the local
configuration change and restoration, not external wire levels. A complete
H4 Command Complete for opcode0x0C03/status0 is needed for result0; credits may
have values other than1. A nonzero status proves a response but fails Reset.
`primary_result=0` with failed cleanup means no earlier classified error, not
successful HCI reception. Raw SR/GPIO/DMA control values are sampled before
Close; successful final NDTR/count and the byte copy are taken after DMA stops.

Actual-C host tests exercise successful response after a prior transport
error, no response, wrong opcode, nonzero status, TX submission/timeout,
UART errors, final RX byte/error and instant TX completion/error boundaries,
failed DMA abort, active-HCI/H4 rejection, START/STOP conflicts, sequence
publication and snapshot rejection during publication. O0 andOs each pass551
assertions, with the three modified production C modules also compiling under
Wall/Wextra/Werror. This model is not a real-radio result; root-owned on-device
execution and its image-bound evidence determine the hardware outcome.

## 2026-09-21 single-phone Product

Only role0 (PHONE) is active. Role1 (ELM) and role2 (PHONE2) are reserved,
not remapped. One HCI connection, one RFCOMM multiplexer/channel and three
L2CAP channels retain SDP server plus SPP. The six-key persistent database,
8KiB task stack, RX2KiB/TX1KiB queues and ACL payload limit are unchanged.
A pending or cancelling session occupies the only slot. A second or duplicate
incoming peer is declined without clearing the first peer's buffers.

Outbound inquiry/SDP client/connect/legacy PIN APIs return UNSUPPORTED.
Phones initiate connections; new SSP pairing requires the explicit pairing
window. Stored keys still support reconnects. Diagnostics version2 retains
three link records for existing tools; retired records remain zero.

Phone GPS fixes, notifications, media, remote control and the updater use the
single NDCP session. No independent OBD or external NMEA device is polled.
The raw-reset/DMA/quiesce diagnostic paths and controller revision selector
are preserved. ARM service tests cover admission, queue saturation, epochs,
late opens and bounded cancellation; they do not prove physical RF operation.
