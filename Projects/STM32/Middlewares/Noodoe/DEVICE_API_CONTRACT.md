# 장치 API 계층 계약

2026-09-12 사용자의 후속 지시: 모든 페리퍼럴을 브링업하고, 상위의
`DoSomething(value)`와 실제 레지스터·장치 커맨드 사이에 장치 서비스 계층을 둔다.
BT와 조도 센서 복구를 우선하며, 아래 문서는 전체 이행 완료를 뜻하지 않는다.

```text
상위 앱·그래픽 / 공개 API
        ↓ 요청(value) → 접수 결과·operation ID
장치 서비스 / 요청 큐·상태 머신·시간 제한·완료 결과
        ↓ 담당 태스크에서만 실제 작업
BSP 드라이버 / 핀·버스·장치 커맨드·전송 완료
        ↓
HAL·레지스터 / UART·I²C·SPI·타이머
```

## 공개 API

- 요청은 유한 크기 큐 또는 단일 요청 슬롯에 복사하고 즉시 반환한다.
  공간 부족은 BUSY로 알리며 빈 슬롯을 기다리지 않는다.
- ACCEPTED는 접수 의미다. 하드웨어 성공으로 취급하지 않는다. 비동기 작업은
  operation ID와 완료 상태/오류를 조회할 수 있게 하고, 이전 연결의 늦은
  콜백이 새 작업을 완료시키지 못하도록 연결 세대를 함께 검사한다.
- 센서 값·연결 상태는 캐시된 snapshot을 복사해 반환한다. 유효성, 시각,
  stale 여부, 최근 오류를 포함한다. 조회 호출이 버스 전송을 시작하지 않는다.
- 호출자의 버퍼를 즉시 재사용할 수 있는 복사 API와 수명 계약이 필요한
  대용량 전송 API를 명확히 구분한다.
- UI/상위 태스크는 HAL 대기, sleep, 연결 대기, flash WIP 대기에 들어가지 않는다.

## 장치 서비스

- 장치마다 담당 실행 문맥을 정한다. 상태 머신이 초기화, 요청 실행, 타임아웃,
  취소, 제한된 재시도를 맡는다. ISR은 완료/오류 정보만 전달한다.
- 초기화 실패는 기록하고 제한된 backoff 또는 명시적 재시도로 복구한다.
  무한 busy-loop나 실패를 숨기는 강제 READY 처리는 하지 않는다.
- 취소 접수 후 늦게 완료된 연결·DMA도 정리해야 한다. 중단 실패 시 자원과
  버퍼를 재사용 가능하다고 알리지 않는다.
- 외부 장치가 없거나 현재 SWD만으로 입증할 수 없는 결과를 PASS로 표시하지 않는다.
- 드라이버 내부의 유한 polling이 남은 이행 단계에서는 해당 작업을 낮은 우선순위
  담당 태스크에 격리하고, 제한 시간과 다른 서비스에 주는 영향을 기록한다.
  이것을 드라이버까지 완전 비동기화했다고 표현하지 않는다.

## BSP 드라이버

- 핀, 레지스터, 장치 주소/커맨드, byte order와 전송 부작용을 소유한다.
- 화면 배치, 앱 상태, GPS 소스 선택 같은 정책을 알지 않는다.
- 오류 시 HAL 상태와 실제 원인 레지스터를 구분해 기록한다. I²C SR1.ARLO와
  AF는 서로 다른 사실이며, 일반 HAL_ERROR를 곧바로 NACK로 번역하지 않는다.
- Cube 관리 파일은 USER CODE 연결부만 사용하며, 기본 IOC 설정과 명시적인
  런타임 진단 설정(예: I²C 100kHz 시험)을 구분한다.

## 현재 이행 우선순위

UART도 `Middlewares/Noodoe/Vehicle/DashService`를 통해 같은 계약으로 이행했다.
Enable/Stop/Reconnect는 operation ID와 실제 UART TC 완료를 보고하고,
Light override는 RAM 정책 적용 완료를 보고한다. I/O task 하나가 파서·TX를
소유하고 상위 getter는 캐시만 복사한다. 하위 HAL 송신은 DMA이며 오류
복구의 bounded abort는 owner task에서만 호출한다. 상세와 실측 범위는
`Middlewares/Noodoe/Vehicle/README.md` 및 `analysis/2026-09-12-uart-bringup`에 기록한다.

Ambient 요청은 operation ID와 완료 결과를 제공하고, BT의
`Bluetooth_RequestStart()`는 요청 번호에 대응하는 접수 ACK와 완료 결과를 제공한다.
기존 BT `Connect/Disconnect/Pair/Discover/Forget/Stop` 등은 즉시 큐 접수 결과를
반환하지만, 요청별 operation ID·완료 결과까지 제공하지는 않는다. 접수 뒤 담당
태스크에서 거부된 명령은 전역 `command_rejected`에만 집계될 수 있으므로,
`GetLinkState()`와 진단 변화가 특정 호출의 완료를 증명한다고 해석하지 않는다.
중간 계층의 소유권·큐·실패 처리는 구현했으며, 모든 BT 명령을 동일한 완료 API로
개편한 상태는 아니다. 최초 `Bluetooth_Start()`는 Storage worker가 한 번 호출해
정적 태스크를 생성하는 초기화 경로다.

다음 API 이행 범위는 BT 연결·해제의 요청 ID와 세션 세대에 연결된 완료 결과를
우선하고, 이어 검색·페어링·키 삭제·정지의 완료 및 실패 조회를 적용하는 것이다.
기존 호출자의 의미와 공개 헤더를 바꾸는 작업은 별도 구현·검증 단계로 남는다.

1. BT/조도 센서의 순정 비교와 실물 실패 원인 확인.
2. 조도 요청·snapshot·재시도 서비스를 통한 400/100/80kHz 진단과 명시적 ID 읽기 진단.
3. BT의 SDP/RFCOMM 대기 제한, 취소와 늦은 완료의 정확한 처리.
4. 검증된 같은 계약을 나머지 장치 API로 적용. 기존 LCDTest와 Cube 재생성 계약 보존.
