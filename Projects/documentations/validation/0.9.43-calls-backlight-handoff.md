# 0.9.43 — incoming calls, auto brightness and update handoff

## What changed

- Incoming cellular calls can now be detected by the riding service even when
  Android has not bound the companion InCallService. The existing Telecom Call
  objects remain preferred. A phone-state listener plus aggregate call-state
  polling supplies the fallback; permission revocation and service shutdown
  detach it. The small ringing-state packet goes before caller-image preparation.
- Calls appear as an overlay without changing the current menu or bookmark.
  O short dismisses only the popup; DOWN short answers; UP long (0.8 seconds)
  rejects/ends. State, connection generation, target ID and permissions are
  checked before action. A held key cannot accept a newly arrived call. Duplicate
  action requests are suppressed while the reported call state is unchanged.
  Existing emergency, installation, fuel-warning and PH9 rules remain.
- Separate phone-state and answer/end permission rows and localized help were
  added. Android 8 has the public answer API but no public endCall API; the UI
  directs the user to end on the phone when no supported Telecom Call exists.
  These are cellular/Telecom paths, not a claim that every third-party VoIP app
  supplies a controllable call. Phone/headset audio routing is unchanged.
- The A1 light classifier's index runs from day=0 to night=9. The LCD PWM policy
  incorrectly used that index in the same direction. It now maps day toward
  99% and night toward 10% at default bias. Positive bias increases brightness.
  Vehicle UART light classification, manual brightness, SUPER NITE, welcome
  policy and normal OFF behavior are preserved.
- EVE FIFO writes now batch into a fixed 256-byte buffer, governed by existing
  command-FIFO credits. A 1,028-byte command stream supplied in 257 tiny calls
  uses five payload calls with identical bytes/order. Partial writes flush at
  deselect, errors stay sticky, and failed payload is not replayed. Ordinary
  RAM/register transactions and actual swap-retirement rules are unchanged.

## Installation log and persistence defect

The uploaded failure log identifies the executing Product as **0.9.41** and the
target as **0.9.42**. All 393,216 Product bytes were verified; FINISH, COMMIT and
RESET were acknowledged. The host reconnected to the old Product. Its restart
trace stopped in pairing persistence rather than image transfer.

The same log reports **3,686,400 baud and six successful local probes**, with
host key generation 1 and persisted generation 0. This demonstrates local UART
probe success in that session; it does not prove RF stability or durable keys.

A reproducible persistence defect was found: a Dark-only build tried to restore
six Light-mode settings through descriptors excluded from that build. The absent
descriptors could mark the shared settings journal corrupt and inhibit later
writes, including Bluetooth keys. Dark-only builds now leave those stable field
IDs opaque and preserved. They do not reject or overwrite them. The actual ARM
regression boots with the six stored fields, saves a new pairing generation,
reboots, and verifies both the key and preserved settings: 22 assertions at
O0 and Os. The previous implementation fails this scenario. The uploaded trace
is consistent with this mechanism; the failing unit's exact settings NOR was
not available, so this is not a proven exclusive physical cause.

The diagnostic reader also sent A5 without its required connection epoch.
It now obtains the epoch from A9 and submits an eight-byte read-only query.
Product permits that read-only query during an update without starting a riding
session or clearing phone models. Mutating retry requests retain their guards.

**An already-running old Product must still perform its own restart handoff.**
This release cannot retroactively repair its in-memory storage state. The new
APK does not bypass key persistence, COMMIT validation or active-write guards.
The existing explicit retained-data stock/Bootstrap recovery route remains
available where the installed recovery implementation responds. An old locked
unit has not been remotely unlocked or tested by this release.

## Rendering and GPS evidence

The GPS test/parked-button/five-second-freshness fixes from 0.9.42 remain. No new
map format or raster implementation is introduced. A real Korea Mapsforge
fixture passed the Android map-feed tests. A 312-byte Seoul vector payload was
decoded by the actual firmware and rasterized into the EVE preview. The waiting
text region remained identical across 12 comparisons over 120 frames.

The existing full-screen fuel veil was rechecked rather than replaced again:
Low/Critical across riding, Welcome and parked-return, plus seven warning
animation phases. Measured background gain was about 6.7–7.6% in clock, ODO,
outer-ring and wallpaper regions. Eighteen injected predecessor-state cases
were pixel-identical to the clean warning frame. Captures include the initial
large icon, transition and final text phases.

The actual ARM/LVGL/EVE sequence replay covered 1,203 frames with transitions,
dense maps, popups, fuel warnings and delayed resource retirement. Peak compact
DL: **4,756/8,192 bytes**, raw: 5,000 bytes. GPU and shade overwrites: zero.
Eighteen raw-versus-compacted frames were pixel-identical. Five call popup
captures peaked at 2,908 DL bytes with no GPU collision.

**There was no physical LCD, phone-call or RF test. Actual 30fps, disappearance
of the reported stutter/tearing, real incoming-call reliability, and the owner's
GPS/fuel-warning symptoms remain unconfirmed on hardware.** Command-call count
reduction and simulation frame validity are not measured FPS.

- 48 Android cases passed, zero skipped/failures: calls, permissions,
  diagnostic snapshot, GPS test UI, location feed, encoding, map feed and vectors.
  Call API cases include Android 8, 9 and 15 models; the public Telecom adapter
  uses mocks. Android 15 initially hit a Robolectric escaped-space SDK path bug;
  the final run uses the same installed SDK JARs via a project-local path.
- APK lint: 0 errors, 0 fatal, 135 warnings. The missing new translations were filled
  in Korean, English, Japanese, Spanish, simplified and traditional Chinese.
- 13 ARM suites plus the targeted persistence regression passed. Runtime input
  replay: 10,000 sequences / 210,001 assertions. FIFO: 293 assertions each at
  O0/Os. Light classifier/PWM: 16,069 each at O0/Os/Oz.
- Resource installation passed O0/Os, including 715 power-loss boundaries that
  preserve the active slot, damaged-input rejection and old resource selection.
- One older dashboard fixture still supplied raw RELEASE directly to UiState;
  it now supplies normalized actions as required since 0.9.41. Production input
  behavior was not changed to satisfy that obsolete fixture.
- Product Release/Debug and Bootstrap built. Gate is byte-identical to 0.9.42.
  APK signer is unchanged; bundle Product hash matches the APK riding contract.
  The replaceable Mapsforge object kit passed D8, alignment and signature checks.

No font pixels, dimensions, baselines or compiler optimization policies changed.
The user-authorized metric relocation appends **1,016 uncompressed bytes** for
number glyph metrics to the existing resource slot. All previous 21 resource
entries are identical. ARM-compiled initializer bytes match the new resource
table exactly. The new Product requires the matching ZIP resources; the previous

bytes, primarily the fixed EVE batching buffer. Heap and stack reservations are
unchanged. Debug retains 92 bytes above its 2KiB minimum; Release retains more
than its 4KiB minimum. No physical storage layout or Gate journal format changed.

## API references

The implementation uses Android's documented
[TelephonyManager state API](https://developer.android.com/reference/android/telephony/TelephonyManager#getCallState()),
[answer API](https://developer.android.com/reference/android/telecom/TelecomManager#acceptRingingCall())
and [end-call API](https://developer.android.com/reference/android/telecom/TelecomManager#endCall()).
The latter two are deprecated from API29; their documented permission and
minimum-version requirements are enforced, with existing Telecom Call control
preferred when Android supplies it.
