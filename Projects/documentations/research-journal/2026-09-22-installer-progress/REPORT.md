# Installer 6.3.1 — 진행률 및 장시간 검사

## 확인된 결함

`ScopedBackup.poll()`은 실제 진행과 관계없이 180초 후 실패했다. 사용자 사진의
355.8KiB/s에서는 128MiB 한 번 검사에 약 368초가 필요하다. 사진 자체는 7초/2% 시점으로
정상 응답을 보여 주며 실제 중단 직후의 로그는 아직 받지 않았다. 따라서 고정 타임아웃은
확인된 코드 결함이고, 사용자의 모든 실패가 그것 때문이라고 확정하지는 않는다.

원본 해시 기준값 계산과 설치 후 비교가 모두 `preserve`로 표시되어 처음에도 6단계로
나왔다. 마지막 파일 kind가 남아 있는 것을 그대로 붙여 ‘부팅 기록’이라는 잘못된 설명도 나왔다.

## 수정

- 긴 읽기 검사는 응답이 아니라 phase/subphase/file별 최고 진행 위치가 증가해야 대기 시간을 갱신한다.
  90초 정체와 30분 절대 상한을 구별한다. 감소·같은 위치·heartbeat만으로 연장하지 않는다.
- 상태만 조회한다. 타임아웃이 났다고 소거/프로그램/COMMIT/RESET을 재전송하지 않는다.
- 처음은 `baseline`, 마지막은 `preserve`로 분리한다. 저장소 전체 검사에 남은 파일 kind를 붙이지 않는다.
- 전체 단계 완료 비율과 현재 작업 바이트 진행률을 각각 표시한다. 전체 단계는 시간 추정이 아니라고
  명시한다. 현재/완료/앞으로 할 단계 목록과 현재 단계의 이유를 제공한다.
- 오류 시 마지막 바이트 위치를 남기고, 단순 전송 완료로 전체 100%를 표시하지 않는다.

## 설치 과정

순정→Bootstrap 전송은 별도 작업이다. 이미 Bootstrap이 실행 중이면 반복하지 않는다.
이후 ‘3. 설치도구→CFW 설치 계속’ 작업은 아래 순서다.

1. 기기/ZIP/UID/BL 대조 및 기기의 Install CFW 선택 확인.
2. FAT·디렉터리·예약영역 검사와 빈 공간 계획.
3. 누도 내부에서 변경하지 않을 외장 NOR 영역의 설치 전 SHA-256 계산.
4. 변경 대상 9개 파일 영역(4.1875MiB)과 메타데이터의 원본을 폰에 보관.
5. 순정 복구본, 폰트/BT 자산, 빈 설정/사진, 누적 기록, 로그, CFW A/B 및 부팅 기록 준비.
   각 파일은 전송/내용 검증/FAT 계획 비교/실제 기록/물리 readback을 수행한다.
6. 누도 내부에서 같은 원본 영역 해시를 다시 계산하고 설치 전 값 및 최종 FAT 계획과 비교.
7. Gate+Product 설치 이미지 전송과 검증.
8. 누도에서 설치 확정 대기.
9. 설치·재시작, 앱 재접속.
10. 60초 정상 실행·BT·후보 버전 확인 후 확정.

128MiB는 해시의 검사 범위이며 폰으로 전송하는 사진의 양이 아니다. 기존 순정 앨범은
덮어쓰지 않는다. 사진에서 측정된 속도로 두 해시 검사만 약 12.3분이므로 이 기기에서
최초 설치 10분 미만은 현재 달성하지 못했다. 이번 수정은 검사 생략을 통한 속도 조작이 아니다.

## 순정 재연결

사용자는 순정에서 연결할 때마다 재페어링이 필요하다고 했다. 실제 실패 로그가 없으며
ADB에 폰이 연결되지 않았다. 원인 확정/실차 해결 완료를 주장하지 않는다.

앱의 보안 SPP 연결 단발 시도를 최대3회 새 소켓으로 바꾸고, 실패한 소켓을 닫은 뒤
공개 `fetchUuidsWithSdp()`로 서비스 정보를 재조회한다. 같은 기기의 ACTION_UUID만 수용한다.
bond 삭제, insecure socket, 숨은 RFCOMM 채널 강제 연결은 사용하지 않는다. 이 재시도는
프로토콜 바이트 전송 이전에만 수행한다. 기기 연결 상태·SDP·시도 횟수·순정 raw/framed
핸드셰이크 단계 로그를 남긴다.

순정 raw 응답 뒤 framed 이벤트가 같은 RFCOMM read에 섞이면 기존 파서가 거절하던 오류도
수정했다. read 경계를 패킷 경계로 가정하지 않고 나머지를 framed decoder에 넘긴다.

비교한 순정 APK 소스: `SunraySPPHandler.java`의 secure RFCOMM 생성/연결,
`BTServices.java`의 표준 SPP UUID. 별도 `SPPServiceReconnectManager`의 서버 UUID는
현재 사용 경로 증거가 없어 새로 광고하지 않았다.
API 근거: https://developer.android.com/reference/android/bluetooth/BluetoothDevice#fetchUuidsWithSdp()

## 적용

APK 버전6.3.1/code3, 동일 앱 ID·서명으로 업데이트한다. 앱을 삭제하거나 데이터를 지우면 안 된다.
기존 6.3 ZIP `3e0f8bb6a724…`와 Bootstrap/Gate/CFW/NOR 형식은 변경하지 않았다.
첫 검사 도중 읽기만 실패한 저널은 기존 안전 재시작 경로로 새 검사 계획을 만든다.
FAT 파일 생성에 들어간 뒤 실패한 작업을 임의로 초기화하거나 새 설치로 취급하지 않는다.

최종 시험 수·APK SHA와 게시 링크는 verification-summary.json 및 github-release.json 참조.
