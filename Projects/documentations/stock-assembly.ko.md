# 순정 펌웨어 어셈블리에서 하드웨어 브링업 정보를 읽어낸 방법

이 문서의 질문은 “순정 펌웨어가 업데이트를 어떻게 하는가”보다 앞선다. **이 보드의 MCU는 어떤 계열이고, 어떤 주변장치와 외부 칩이 연결되어 있으며, 그걸 새 BSP에서 어떻게 안전하게 다시 켜는가?** 순정 V5.16의 Thumb 명령, 복원한 초기 RAM 데이터, 순정 앱의 통신 코드와 실기기 관찰을 어떻게 조합했는지 설명한다. 원본 펌웨어 바이너리나 전체 디스어셈블리 출력은 저장소에 공개하지 않는다. 주소는 조사한 이미지 **SHA-256 3b64673054ca84b9cf504f4cc7ebcb2e6615b9fbf59df79a37a92dcf14f037ca**에서만 유효하다.

## 먼저 “명령어가 맞는지” 확인했다

순정 OTA APP는 458,748바이트이고 MCU 주소 **0x08010000**부터 로드된다. 처음 두 워드는 초기 MSP **0x20025318**과 Reset 벡터 **0x08076719**다. ARM Cortex-M의 벡터 맨 끝 비트는 Thumb 상태를 뜻하므로 실제 명령 시작은 0x08076718이다. APP의 SystemInit 0x08073E90은 VTOR을 0x08010000으로 바꾼다. 이 사실은 APP의 링커 시작점과 인터럽트 테이블 위치를 결정한다. 0x08000000–0x0800FFFF는 OTA APP에 포함되지 않는다.

이후 각 후보 함수를 다음 순서로 읽었다.

1. 벡터·직접 호출·분기에서 함수 경계를 찾는다. ARM Thumb는 16/32비트 명령이 섞이고 PC 상대 리터럴 풀이 코드 사이에 있으므로, 임의 주소부터 연속으로 분해한 모든 줄을 명령으로 믿지 않는다.
2. STM32F4의 **주변장치 기준 주소**를 리터럴에서 찾는다. 예를 들어 0x40013000은 SPI1, 0x40000C00은 TIM5다. 단순히 상수가 있다는 것보다, 그것을 핸들의 Instance 필드에 쓴 뒤 HAL 초기화 함수를 호출하는지 확인한다.
3. 핸들 구조체에 기록하는 상수의 오프셋을 HAL 구조체와 대조해 모드·데이터 비트·클록 분주기·DMA 채널을 복원한다. GPIO는 포트 기준 주소, 핀 마스크, Alternate Function, 출력 레벨과 **실제 호출자**를 같이 확인한다.
4. 외부 칩은 내부 레지스터 주소나 버스만으로 단정하지 않는다. JEDEC ID, 제조사 고유 명령, 펌웨어 패치 바이트, 표시 칩의 REG_ID처럼 다른 제조사 자료와 맞는 **식별값**을 찾는다.
5. 복원한 가설을 IOC·BSP에 곧바로 쓰기 전에 순정 앱·실측 UART·실제 패널 반응으로 대조한다. 먼저 읽기 전용 확인을 하고, 출력·소거·리셋 핀은 위험도를 따로 평가한다.

예외 벡터도 함정이었다. 많은 벡터가 APP 안의 주소를 가리키지만 그 끝은 IAR의 기본 무한 루프 명령 **FF F7 FE BF**뿐이다. 주소가 있다는 이유만으로 SPI1 IRQ나 I2C3 IRQ가 실사용된다고 판단하지 않았다. 확인된 비기본 IRQ에는 UART5, 관련 DMA, TIM2/TIM5, 여러 EXTI, OTG_HS 등이 들어간다. 이는 첫 BSP에서 어떤 경로를 폴링·바이트 IRQ·DMA로 만들어야 할지 정하는 데 중요하다.

## MCU 계열과 메모리부터 좁힌 근거

벡터 순서, Cortex-M4 FPU 명령, GPIO/USART/SPI/FMC 레지스터 주소, ST HAL의 핸들 배치가 **STM32F429 계열**과 맞았다. 초기 스택 주소와 내부 플래시 크기도 그 구성과 양립한다. 이후 실물 전체 플래시 두 번 읽은 512KiB가 바이트 단위로 일치했고, APP 영역은 보존한 V5.16 OTA와 일치했다. 그러나 어셈블리만으로 **패키지 마킹과 정확한 칩 suffix**를 사진처럼 읽을 수는 없다. Cube 프로젝트는 STM32F429IET6으로 설정했지만 이것은 구현 타깃의 선택이다.

순정 SystemInit의 HSI 활성화·RCC 기본값 복구는 **리셋 직후 초기 상태**를 보여줄 뿐 최종 SYSCLK가 아니다. 이미지에 180MHz 상수가 한 번 보인다는 이유로 HSE·PLL 값을 정할 수도 없다. 최종 클록은 RCC 레지스터 실측과 후속 클록 설정 호출 흐름을 대조해 정했다. SDRAM도 FMC 접근 흔적만으로 제조사·타이밍을 복원하지 않고 보드와 읽기/쓰기 시험을 따로 확인했다.

| **외장 NOR / SPI5** | PF7/8/9 AF5와 PF6 GPIO 선택, SPI5 master 8비트 mode 0. 플래시 드라이버는 9F RDID 뒤 **C2 20 1B**를 검사하고 128MiB·4KiB 소거·256바이트 페이지를 가정한다. 이 값은 Macronix MX66L1G45G 자료와 맞는다. MSP의 halfword DMA 설정과 SPI5의 8비트·바이트 전송 wrapper가 공존하므로 최종 전송 단위는 실제 호출 경로를 더 봐야 한다. |
| **LCD 제어 / SPI4** | PE2/PE5/PE6 AF5, 16비트 master·mode 0·DIV16 설정과 10/11/28/29/0A 명령 계열이 보인다. | EVE가 픽셀 렌더링을 맡고 SPI4는 별도 패널 제어로 다룬다. PE4 등 제어핀 극성은 읽기·실측 전에 확정하지 않는다. |
| **차량 데이터 / UART5** | PC12 TX·PD2 RX AF8, 115200 8N1. UART5 IRQ 0x08070E68→HAL IRQ 0x0804C25C→RXNE 0x0804C55C→수신 완료 0x08043C08→F5 파서 0x0804EA14로 이어진다. | **백라이트 / TIM5** | 0x0804351A–0x0804363C은 TIM5 Instance 0x40000C00, ARR 99, 약 50kHz 카운터 목표, CH4 PWM1 active HIGH와 듀티 제한을 보여준다. GPIO MSP 0x08038224–0x08038240은 **PI0 AF2**다. | TIM5_CH4 PWM을 별도 백라이트 서비스로 만들고 낮은 듀티부터 실제 밝기·극성을 확인한다. 0x20022998의 PWM 핸들과 IRQ 쪽 0x2002295C 참조를 같은 객체라고 혼동하지 않는다. |
| **버튼·IGN·선택 스위치** | GPIO 포트·핀 마스크 초기 데이터와 EXTI 호출, TIM2의 주기적 읽기, 순정 입력 허용 조건을 함께 대조했다. PD12/PI6/PA15는 세 액티브 LOW 버튼, PG13은 IGN, PH9는 계기판/누도 조작 선택으로 좁혀졌다. | GPIO 원시값→디바운스→버튼 시간 이벤트→PH9/IGN 정책→화면 동작 순으로 분리한다. 어셈블리의 마스크만으로 하네스 **커넥터 접점 번호**는 알 수 없다. 복구 버튼은 일반 UI 차단 정책과 별개다. |

FT81x나 NOR처럼 **ID·명령 체계가 부품 자료와 일치**하면 계열 판단이 강해진다. 반대로 SPI4의 패널 품번, SDRAM 칩 표기, MCU 패키지, Bluetooth BGA의 실제 실장 리비전은 초기화 코드만으로 확정할 수 없다. I2C1에는 MFi 인증칩으로 해석되는 경로도 보였지만 CFW 브링업 대상에서 제외했고, 다른 I2C 장치를 조도센서라고 섞어 부르지 않는다.

## 실제로 한 주변장치를 복원하는 예: SPI1 화면 경로

첫째, 0x08033C1A에서 받은 인수가 SPI 핸들 구성 동안 r4에 보존되는 것을 본다. 다음 0x08033C40–0x08033CA0에서 핸들의 Instance에 0x40013000을 넣는다. STM32F429의 메모리 지도에서 이 값은 **SPI1**이다. 같은 핸들 오프셋의 모드·방향·데이터 크기·CPOL·CPHA는 각각 master, 2-line, 8비트, 0, 0으로 해석된다. 분주기는 함수 내부의 단일 상수가 아니라 **인수 r4**이므로 호출자 둘을 찾아 /8과 /4를 각각 확인한다.

둘째, SPI1 핸들만으로 핀을 알 수 없으므로 MSP 초기화가 설정하는 GPIO Alternate Function을 본다. PB3·PA6·PB5의 AF5가 SCK·MISO·MOSI 구성과 맞는다. 셋째, SPI 전송 직전 PA4를 LOW로 내리는 함수와 초기화 때 PB1에 LOW/지연/HIGH를 내는 호출을 찾는다. 그래서 각각 CS와 PDN/reset **후보**가 된다. 넷째, 그 SPI에서 읽는 **0x302000의 0x7C**와 EVE 명령 FIFO·480×480 타이밍 상수를 Bridgetek 명세와 비교한다. 이 네 단계가 맞아야 “SPI1에 뭔가 달렸다”에서 “FT81x 계열 화면 경로다”로 올라갈 수 있다.

이후 새 BSP에서는 분주기를 낮춰 REG_ID를 **읽기만** 한 다음 패널 상태·RAM_G·디스플레이 리스트를 순서대로 켠다. 값이 맞지 않으면 SPI 모드·CS·PDN·전원·실장 모델을 다시 확인하지, 식별 실패를 무시하고 사진 데이터를 업로드하지 않는다.

## 순정 명령을 그대로 베끼지 않고 BSP로 옮긴 방식

**레지스터 주소·상수 → HAL 설정 → 안전한 식별 읽기 → 출력 활성화 → 상위 API** 순서로 옮겼다. 예를 들어 EVE는 SPI1 master라는 사실만 알아도 화면이 켜지지 않는다. CS/PDN 후보, SPI 초기·가속 분주기, REG_ID, 패널 시퀀스, EVE RAM_G와 디스플레이 리스트의 swap까지 각각 검증해야 한다. NOR는 SPI5와 RDID를 알아도 곧바로 FAT를 쓸 수 없다. 실제 칩 용량·주소 모드·소거 단위, 순정 FAT와 마지막 업데이트 예약 공간을 먼저 확인해야 한다.

차량 UART는 파서의 입력 구조와 실제 배선 방향을 둘 다 확인했고, 버튼은 인터럽트 발생 자체를 “누름 완료”로 보지 않고 접점 안정화와 길게 누르는 시간을 분리했다. 이렇게 만든 저수준 BSP를 미들웨어 이벤트·비동기 요청이 감싸므로, 화면과 App_Logic은 SPI 레지스터나 NOR 소거 경계를 직접 다루지 않는다.

## 분석 중 바로잡은 두 가지 함정

**벡터가 있다는 이유로 그 인터럽트를 사용했다고 할 수 없다.** 순정 APP의 많은 벡터는 기본 무한 루프로 향한다. SPI·I2C 직접 IRQ를 모두 활성화하면 원본과 다른 드라이버가 된다.

**큰 RAM 임시 버퍼가 있다고 전체를 다시 썼다고 할 수 없다.** 내부 섹터 2/3 갱신 후보 함수 0x080426D4는 16KiB를 RAM에 복사·병합하고 섹터를 소거하지만, 0x080427C4의 상한 비교는 프로그램 루프가 **앞 4KiB**에서 끝난다는 것을 보여줬다. 초기 문서의 “16KiB 전체 보존 재기록” 설명은 틀렸다. 이 함수의 모든 호출자와 나머지 12KiB 사용법은 확인되지 않았으므로 실제 데이터 손실이 있었다고도 단정하지 않는다.

발췌한 명령에서도 할당량과 쓰기 상한이 다르게 보인다.

| 주소 | 순정 명령의 요지 | 의미 |
|---|---|---|
| 0x08042716 | mov.w r0, #0x4000 | 16KiB 임시 버퍼를 준비한다. |
| 0x080427C4 | adds.w r0, r7, #0x1000 | 쓰기 루프의 비교 상한은 섹터 시작+4KiB다. |
| 0x080427C8–0x080427D6 | 주소 비교 후 word program 호출 | 상한에 도달하면 더 이상 프로그램하지 않는다. |

## 원자료와 적용 범위

본문의 주소·분주기·DMA stream과 핀은 해당 V5.16 이미지의 분석값이다. 자세한 함수별 명령어·리터럴 검사는 [SPI·PWM 재확인 보고서](research-journal/2026-09-12-cube-bsp-crosscheck/README.md), [MCU 주변장치 분석](research-notes/ak550-sr15-mcu-peripheral-settings.md), [UART/클록 정정](research-notes/2026-09-09-ak550-firmware-uart-boot-review.md)에 있다. [순정 전체 플래시와 OTA 대조](research-journal/2026-09-11-full-flash-ab-verification/README.md)는 분석한 APP가 실물 보드의 것과 같다는 근거다. 부팅·업데이트 명령어 흐름은 [후속 부트 연구](research-notes/2026-09-11-noodoe-bootloader-and-bluetooth-update.md)에서 별도로 다룬다.

이 재구성은 다른 연식/보드 리비전의 회로도가 아니다. 특히 오래된 연구 노트의 미확정 “후보”를 현행 IOC의 확정 값으로 무조건 승격하지 않는다. 실제 다른 기기에 이식할 때는 칩 마킹·FAT·버스 식별값·클록·패널 및 무선 동작을 해당 기기에서 다시 확인해야 한다.
