# Noodoe app data pipeline

Date: 2026-08-30 KST

## Current conclusion

The working public Noodoe app should be treated as the live reference
implementation. The separate Noodoe Tools/test APK is still valuable as a
static protocol reference, but it is not a dependable live experiment tool if
its first-run login is blocked by dead or unreachable servers.

For reimplementation, there are two distinct problems:

1. Transport/protocol: connect to the meter and send valid SPP/RFCOMM frames.
2. Content generation: create the exact files/data that those frames install or
   update on the meter.

The second problem is not just "send this photo" or "send this dashboard JSON".
The app often renders, converts, bundles, hashes, queues, and then transfers
meter-ready artifacts.

## App roles

### Noodoe Tools/test APK

Use for:

- Finding protocol constants, command IDs, UUIDs, and task structure.
- Understanding debug/test flows that may not exist in the public UI.
- Recovering direct hardware assumptions from code paths.

Do not rely on it for:

- Live capture sessions if login blocks the app before it reaches the hardware
  screen.
- Proving that a command is accepted by the AK550 meter.

### Working public Noodoe app

Use for:

- Capturing real SPP bytes while it performs successful meter actions.
- Dumping app cache/temp files after each controlled action.
- Comparing "what the UI selected" with "what bytes were sent".

This app is the dynamic oracle while it still runs.

## Pipeline model

Observed and inferred pipeline:

```text
user action / cloud content / route state / phone notification
    -> local model objects
    -> render or convert to meter-ready assets
    -> queue task rows or in-memory transfer tasks
    -> FILE_TRANSFER_NEGOTIATE / FILE_TRANSFER / UPDATE_* commands
    -> meter storage and active display state
```

Known local model/package names include:

- `SunrayCreation`
- `SunrayWidget`
- `CreationBundle`
- `BTTaskStructure.TransferringFileInfo`
- `CMUTaskContract.CMUTask`

## Concrete evidence from the public app

### Navigation image generation

`ImageGenerator` renders Android views to bitmaps, crops them, and stores the
result as JPEG or PNG files before transfer.

Evidence points:

- It stores generated files under a `STORE_DIRECTORY`.
- It captures view drawing caches.
- It writes JPEG at quality 35 for several navigation summary images.
- It writes PNG for text/road assets.
- It has a 40960-byte file limit and recompresses JPEGs at lower quality when
  needed.
- Generated filenames include a key hash and timestamp.

This proves that navigation is not sent only as text and coordinates. It uses a
mix of control fields plus pre-rendered image assets.

### Navigation transfer

`TaskSender` wraps generated image files into
`BTTaskStructure.TransferringFileInfo`, assigns file/cache IDs, sends files via
`addNavigationFile`, and then sends `sendNavigationUpdate` with file ID
references.

This means the meter can cache image files, and later update commands refer to
those cache IDs.

### Creation/dashboard bundling

`CreationBundler` converts creation widget/background state into a
`CreationBundle`.

Evidence points:

- Background widgets can be flattened.
- PNG-like background material can be converted to JPEG.
- Output files are renamed by MD5.
- A generated `.cfg` configuration file is also renamed by MD5.
- The bundle contains widget definitions and a map of generated files.

This suggests dashboards, clocks, speedometers, and weather creations are
packaged assets plus configuration, not simple raw app-side JSON.

### Task queue and byte materialization

`TaskContentUtils` reads rows from the CMU task provider and materializes bytes
from several sources:

- Hex strings.
- File paths/URIs.
- Resource files.
- Testing/generated byte arrays.

For install-type tasks, it can combine command header bytes with loaded file
bytes before the lower Bluetooth layer sends them.

## Feature implications

### Clock

Clock sync is mostly protocol-level. It is the best first independent-client
target because the payload is small and visible on the meter.

### Phone notifications

App notifications are also mostly protocol-level: app ID, app name, and
notification text. They are a good second target after reliable SPP framing and
ACK handling.

### Weather

Weather has a small structured update command, but weather-themed dashboard
assets may still depend on creation files already installed on the meter.

### Gallery/photo transfer

The user-selected phone image is likely cropped/resized/re-encoded into a
meter-acceptable file before transfer to the `GALLERY` location. The exact
gallery transform still needs a controlled capture and app cache dump.

### Dashboard, clock face, speedometer face

These likely require the creation bundle pipeline: widget model,
configuration, generated resource files, MD5 names, then file installation to
the matching location:

- `DEFAULT_DASHBOARD = 0`
- `CLOCK = 512`
- `WEATHER = 768`
- `SPEEDOMETER = 1024`
- `GALLERY = 1536`

This is why capturing only Bluetooth bytes is helpful but incomplete: for a new
Android app or ESP32 client, we also need to know how to build the files being
sent.
