# Noodoe theme preservation and authoring

## What is preserved

The official application has three distinct resource layers. They must not be
described as one collection.

1. **Embedded APK resources** are reproducible from the preserved XAPK. In
   version 2.1.14 this includes `assets/preset`, `assets/fonts`,
   `assets/default_creations`, Android `res`, and the split APK resources.
2. **Downloaded creations** are delivered by the Noodoe service and installed
   into the application's private storage. They are not all present in the APK.
3. **Locally authored and installed bundles** are generated by the official
   editor and cached in private storage. A rooted-device copy is the best
   evidence for exact user-visible themes.

The production application reads catalog IDs from the authenticated Firebase
nodes `presets` and `publicCreationList`, then resolves each ID under
`creations/<id>`. A Creation record names three CDN objects: `appData`,
`previewImage`, and `thumbnailImage`. The `appData` object is a ZIP containing
the editable `creation.json` and source images. It is not the final SPP bundle.

Run the embedded-resource archive from the workspace root:

```powershell
.\tools\archive_noodoe_app_resources.ps1
```

Add `-CopyOriginalPackage` when the archive should contain a second copy of the
preserved XAPK. Every archived file is recorded in `manifest.sha256.json` with
its length and SHA-256 digest.

Archive an individually known online Creation without a login token:

```powershell
python .\tools\archive_noodoe_themes.py --creation-id <CREATION_ID>
```

Archive every theme visible to the signed-in official app using a Firebase ID
token stored in a temporary file:

```powershell
python .\tools\archive_noodoe_themes.py --id-token-file .private\firebase-id-token.txt
```

The tool also accepts `--custom-token-file` or `--app-data <EXTRACTED_DATA>`.
In the latter case it reads `firebase_token` from the official default shared
preferences and exchanges it in memory. Token values are never written to the
archive or printed. Remove temporary token files after collection.

## Bundle contract

A dashboard creation is a content-addressed set of files:

- One UTF-8 JSON `.cfg` file describes `configuration.widgets` and lists every
  payload filename in `files`.
- Payload filenames are the lowercase MD5 of their exact bytes plus their
  extension.
- The `.cfg` filename and transfer `contentId` are the MD5 of the exact serialized
  `.cfg` bytes.
- Clock content is transferred to location `0x01`; speedometer content uses
  location `0x04`.
- A successful transport commit does not prove that the dashboard renderer
  accepted the widget schema. Renderer behavior must be verified on the unit.

## OpenNoodoe authoring policy

The normal UI does not generate an arbitrary `BackgroundWidget`-only file.
Earlier vehicle tests showed that syntactically valid but unsupported widget
combinations can transfer successfully and then fail in the renderer.

The first authoring path therefore clones one of the known working clock or
speedometer bundles, keeps its validated widget structure, replaces the 480 x
480 background, applies only exposed CFG options, and recalculates all affected
MD5 identities. The complete generated bundle is saved in the app-private
`files/themes` repository before transfer, so it remains selectable from the
theme library even when the vehicle is disconnected.

The beta application exposes two deliberately separate user paths:

1. **Preserved official themes** reads an HTTPS static catalog, downloads a
   compiled bundle ZIP, checks the catalog SHA-256, validates the cfg/content
   MD5 contract, stores the full bundle locally, and then transfers it.
2. **Create theme** crops a photograph to the circular 480 x 480 dashboard
   area, applies exposed CFG choices to a vehicle-validated clock or speedometer
   template, stores the result, and transfers it.

Build a hostable static repository from compiled bundle directories:

```powershell
python .\tools\build_noodoe_theme_repository.py
```

The generated `preservation/theme-repository/dist/catalog.json`, `bundles/`,
and `previews/` tree can be hosted unchanged on any HTTPS static host. Add an
entry to `repository-sources.json` only when its source directory contains the
actual compiled transmission bundle. The current sample catalog contains two
captured, vehicle-validated references; it is not a claim that the complete
official online catalog has already been archived.

The full official collection requires either a rooted copy of each official
app `files/installed/<type>.bundle` after installation or a faithful clean-room
implementation of the official `CreationBundler` conversion from `appData.zip`.
Raw online `appData.zip` files must remain in the editable-source archive and
must not be published as ready-to-transfer bundles.

## Rooted-device collection

Before modifying or clearing the official app, acquire its private data
read-only. Preserve the entire package directory rather than guessing one cache
path because version and Android storage behavior differ.

The reproducible collector performs the tar acquisition, device/local SHA-256
comparison, installed-APK copy, package dump, and local extraction:

```powershell
.\tools\collect_noodoe_official_app_data.ps1 -Serial <ADB_SERIAL> -StopApp
```

Omit `-StopApp` for a live snapshot. Stopping the app gives the more consistent
SQLite/preferences snapshot and does not clear its account or data.

```powershell
adb shell su -c "tar -C /data/user/0 -cpf /data/local/tmp/com.noodoe.sunray.tar com.noodoe.sunray"
adb pull /data/local/tmp/com.noodoe.sunray.tar evidence/official-app-device/
adb shell su -c "sha256sum /data/local/tmp/com.noodoe.sunray.tar"
Get-FileHash evidence/official-app-device/com.noodoe.sunray.tar -Algorithm SHA256
```

Also collect `/data/data/com.noodoe.sunray` if it resolves differently on the
target Android version, plus an APK inventory from `pm path com.noodoe.sunray`.
Do not log into, update, clear, or uninstall the official app before this copy.

The important private paths observed in the official implementation are:

- `files/collected/<creationId>`: downloaded editable Creation archive.
- `files/installed/<type>`: the currently installed editable archive.
- `files/installed/<type>.bundle`: generated `.cfg` and hashed transmission files.
- `files/remix/<creationId>/...`: downloaded source used for remix/edit.
- `files/local_creation`: local Creation metadata and preview cache.

## Next authoring stages

The preserved `preset` tree and decompiled widget serializers define the next
editor stages: clock hands and marks, digital fonts, date placement, speed bars,
needles, odometer positions, colors, and animation flags. Each control should be
enabled only after a generated bundle has passed schema validation and a real
dashboard render test. This keeps preservation evidence separate from inferred
features.
