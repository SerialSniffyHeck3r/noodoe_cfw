# 순정 V5.16 문자·폰트 조회 분석

2026-09-22. 내부 FLASH A 덤프의 원본 Thumb 코드를 분석하고 문자 디코더·폰트 선택·파일 읽기 요청을 오프라인 실행했다. 원본과 장치에는 쓰지 않았다.

## 확인한 결론

순정 앱은 문자별 고정 길이 글리프 레코드를 파일에서 읽는 경로를 갖는다. CJK 전체 글리프가 512 KiB 내부 FLASH 덤프에 내장된 구조로 설명할 수 없다. 한글 완성형 전체를 조회하는 코드 범위는 있지만 실제 폰트 파일의 모든 레코드가 정상 글리프인지는 확보 자료로 검증하지 못했다.

| 주소 | 역할 |
|---|---|
| `0801C51C` | UTF-8 1/2/3바이트를 16비트 문자 값으로 변환. 4바이트 문자는 값 1로 대체 |
| `08020878` | 16비트 문자 값으로 폰트 파일의 범위 시작값 선택 |
| `08020A46` | `\font\N%04X`, 글자당 1231바이트 레코드 |
| `08020AD2` | `\font\R%04X`, 글자당 963바이트 레코드 |
| `08020788`, `08020800` | 파일 열기, 위치 이동, 고정 길이 읽기, 첫 바이트와 후속 데이터 처리 |
| `08076990`, `0807699C` | 위 두 파일 경로 형식 문자열 |

N/R의 명칭·서체 이름은 확인하지 않았다. 파일 읽기 함수는 첫 바이트에 각각 41 또는 37을 곱한 값을 반환하며, 뒤의 데이터를 저장 계층 함수 `080334B0`에 넘긴다. 이 함수를 일반 CPU memcpy라고 부르면 안 된다. 실제 픽셀 포맷·서체 모양은 이번 범위에서 확정하지 않았다.

파일 위치 계산:

```text
N offset = (문자 코드 - 선택된 범위 시작값) * 1231
R offset = (문자 코드 - 선택된 범위 시작값) * 963
```

한글 `U+AC00..U+D7A3` 11172개에 대한 범위 비교와 시작값 `AC00` 반환을 확인했다. 이는 초성·중성·종성을 합성하는 경로가 아니라 완성형 코드별 레코드를 조회하는 경로다.

## 원본 코드 실행 예

| 문자 | UTF-8 디코더 결과 | 파일/동작 |
|---|---|---|
| 가 | `AC00` | `NAC00`/`RAC00`, offset 0 |
| 한 | `D55C` | `NAC00` offset 13033828, `RAC00` offset 10196244 |
| 힣 | `D7A3` | `AC00` 그룹의 마지막 완성형 레코드 |
| あ, ア | `3042`, `30A2` | `N3000`/`R3000` |
| 中 | `4E2D` | selector byte 2에서는 `N4E00`/`R4E00`, 값 1에서는 `N3000`/`R3000` |
| 𠀀 (`U+20000`) | `0001` | 파일 조회 대신 내부 FLASH의 대체 데이터 사용 |

selector byte는 SRAM `20022DA5`다. 언어별 파일 분할과 관련된 것으로 보이지만 이 바이트의 상위 의미를 이번 분석에서 별도로 확정하지 않았다.

4바이트 UTF-8 문자를 대체하므로 이 경로는 Unicode의 CJK 확장 영역 전체를 지원하지 않는다. 한글 범위 전체 레코드를 두 종류 모두 채운다면 약 23.38 MiB가 필요하다는 계산은 가능하지만, 실제 설치 용량 또는 실재 파일 크기를 측정한 값은 아니다.

내부 FLASH의 대체 데이터 시작점은 N=`08067CC4`(1230바이트), R=`08069A58`(962바이트)다. 따라서 내부 FLASH에 글자 관련 데이터가 하나도 없다는 의미도 아니다.

## 검증 범위와 한계

`inspect_fonts.py`는 Capstone으로 어셈블리를 남기고 Unicorn으로 원본 코드를 실행한다. 18개 문자/selector 조합에서 두 로더를 검사했다. 파일 open/seek/read, 문자열 포맷 함수, 저장 계층 write는 mock이다. read에 넣은 값은 합성 데이터이며 실제 폰트 복원 또는 실물 표시 검증이 아니다. 결과는 `evidence.json`.

기존 도너 USB 이미지에서는 `font` 디렉터리가 손상돼 정상 폰트 파일을 확보하지 못했다. 자세한 기존 관측은 [USB 획득 문서](../../docs/2026-09-09-noodoe-usb-acquisition.md). 따라서 코드의 조회 가능 범위와 실제 설치된 글리프 커버리지를 구분한다.
