# FROMDASH-GAS1 / fuel0: 실물 연료계 1칸·0칸과 payload 0x51·0x50

2026-09-10. 사용자 관측: AK550 실물 연료계가 총 5칸 중 **1칸이면 FROMDASH-GAS1, 0칸이면 lower-fuel0**이다. 두 원본의 행 경계를 연결하고 길이와 XOR가 맞는 프레임을 서로, 그리고 기존 LOWERPIN과 비교했다. 장치 송신이나 원본 수정은 하지 않았다.

## 0칸과 1칸의 직접 비교

| 실제 연료 표시 | 파일 | 정상 프레임 | payload 3 | 상위 / 하위 니블 |
|---|---|---:|---|---|
| 0칸 | lower-fuel0.tsv | **23개 전부 정상** | **50** | **5 / 0** |
| 1칸 | FROMDASH-GAS1 | **33개 정상** | **51** | **5 / 1** |

```text
0칸: F5 21 09 | 00 00 00 50 7B 8E 00 00 00 | 78
1칸: F5 21 09 | 00 00 00 51 7B 8E 00 00 00 | 79
```

**payload 3의 하위 4비트가 실제 연료 표시 0칸·1칸에 각각 0·1로 대응함을 실측으로 확인했다.** 두 캡처의 다른 payload 바이트는 모두 동일하다. 상위 니블은 두 상태 모두 5이며, 실물 총 5칸이라는 정보와 맞아 총 칸 수 후보가 유력하다. 다만 상위 니블의 의미나 2~5칸의 인코딩까지 확인한 결과는 아니다.

이전 LOWERPIN의 payload 3=00은 이번 정상 0칸=50과도 다르다. 따라서 이전 전부 0 상태를 곧바로 정상적인 빈 연료계와 동일시하지 않는다. 당시 차이가 센더 미연결·정보 유효성·다른 상태 때문인지는 미확인이다.

## GAS1과 이전 LOWERPIN 비교

정상 프레임 **33개 전부**가 다음과 같다.

```text
F5 21 09 | 00 00 00 51 7B 8E 00 00 00 | 79
offset      0  1  2  3  4  5  6  7  8
```

기존 LOWERPIN 정상 116개의 프레임과 비교:

```text
LOWERPIN: F5 21 09 | 00 00 00 00 7B 8E 00 00 00 | 28
GAS1:     F5 21 09 | 00 00 00 51 7B 8E 00 00 00 | 79
                             ^^                  ^^
                       payload +3 변경       XOR 변경
```

**payload에서 달라진 것은 offset 3의 00→51 한 바이트뿐이다.** 마지막 28→79는 그에 따른 정상 체크섬 변화다. 첫 payload 바이트가 offset 0이며, offset 3은 전체 프레임을 0부터 셌을 때 offset 6이다.

| 필드 | 기존 LOWERPIN | GAS1 |
|---|---:|---:|
| payload 0: 속도 | 0 | 0 |
| payload 1: 미확인 | 0 | 0 |
| payload 2: 기존 공용 잔량 위젯 raw | 0 | **0, 변화 없음** |
| payload 3: 니블로 분리되는 값 | 0x00 | **0x51** |
| payload 3 하위 니블 | 0 | **1** |
| payload 3 상위 니블 | 0 | **5** |
| payload 4..7: ODO | 36,475km | 36,475km |
| payload 8: 온도형 raw | 0 | 0 |

첫 정상 프레임은 원본 2–3행, Seq 3530–3531, PC 시각 05:23:05.127–05:23:05.132에 걸쳐 있다. 파일이 시작할 때부터 이미 51이다. 따라서 캡처 안에서 연료 표시가 0칸에서 1칸으로 전환한 시점을 잡은 것은 아니다.

## 해석과 기존 후보의 수정

`0x51`을 `상위 5 / 하위 1`로 분리하는 연산은 V5.16 펌웨어에서 이미 확인됐다. 이번에 사용자가 확인한 **총 5칸 중 1칸**과 잘 맞는다.

따라서 **상위 니블=총 칸 수, 하위 니블=현재 표시 칸 수**가 현재 해석이다. 연료 표시와 연동해 우선 관찰할 위치는 payload 3이며, 하위 니블 0·1은 fuel0 추가 캡처로 각각 0칸·1칸과 대응했다. 상위 5가 총 칸 수인지 특정 상태 코드인지는 아직 확정하지 않는다. 두 상태의 대응을 연료 센서 변환식 또는 정확한 연료 퍼센트로 확대하지 않는다.

기존 payload 2→`BatteryWidget`/`fuel_battery` 공용 위젯의 0..5 단계 변환 경로는 코드상 유지된다. 그러나 그 값은 이번에도 0이다. **그 소비 경로를 근거로 AK550 실물의 연료량이 반드시 payload 2에 실린다고 해석해서는 안 된다.** 해당 코드가 분리한 payload 3 니블의 최종 UI 소비 의미는 이번 범위에서 확정하지 못했다. 또한 분석한 V5.16 OTA와 실물 전체 펌웨어의 버전 일치가 검증된 것은 아니다.

다음에 동일한 조건에서 실물 2칸이 표시될 때 payload 3이 **52**, 3칸에서 **53**으로 바뀐다면 `총 칸 수 / 현재 칸 수` 해석을 더 강하게 뒷받침한다. 이는 다음 캡처에 대한 예측이며 아직 관측한 값은 아니다. 그때도 payload 2와 전체 정상 프레임을 함께 비교한다.

## 캡처 품질과 재현

fuel0:

- 원본: `Serial-Capture/diserial-COM11-115200-8N1-lower-fuel0.tsv`, 2,122 B.
- Rx 29행, 299 B. F5 프레임 23개 전부 정상, 행 경계를 넘는 프레임 6개, 정상 프레임 밖 바이트 0개.
- SHA-256: `0c3947871db1e56976cacf6ffda1e11607bd22fc91413a0d0a69b316b8787aa9`
- 추출 스트림 SHA-256: `5939f7f012503b18ba8971289b2934ec0b5679fcc7a835f69a1ff04475a6714b`
- 첫 프레임 원본 2행, Seq 3594, 05:26:46.441부터 마지막 원본 30행, Seq 3622, 05:26:48.747까지 50으로 고정이다. 실제 1칸→0칸 전환을 연속 캡처한 것은 아니다.
- 별도 독립 구현에서도 추출 해시, 정상 23개와 GAS1 대비 payload 3만의 변화를 확인했다.

GAS1:

- 원본: `Serial-Capture/diserial-COM11-115200-8N1-FROMDASH-GAS1` (확장자 없음, TSV 내용)
- 파일 크기: 3,648 B. Rx 51행을 이어 붙인 스트림 513 B.
- SHA-256: `3849cca1ddfc516adcd9194334d758c5945e83d1b8187281ba8cac73aa62a339`
- 추출 스트림 SHA-256: `d40709ad079c35543ea8e20618eacc789a9523f7646076a69a77470e70a5a4a3`
- F5 후보 39개 중 알려진 길이/XOR를 만족한 33개. 나머지 후보 6개는 배제했다.
- 정상 프레임 중 7개가 TSV 행 경계를 넘는다. 정상 영역 429 B, 정상 프레임 밖 84 B. `0x55`는 0개.
- 정상 프레임 외 바이트와 손상 후보를 수정하거나 새로운 명령으로 해석하지 않았다. 후보의 6/39를 물리 UART 손실률이라고 계산하지 않는다.
- 별도 독립 구현도 원본/스트림 해시, 정상 프레임 수, 바이트 차이와 첫 행/시각을 동일하게 확인했다.
