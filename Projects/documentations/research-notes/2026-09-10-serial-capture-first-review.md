# AK550 계기판–Noodoe: 첫 실물 UART 캡처 검토

작성: 2026-09-10. 원본 TSV를 읽기만 했다. 장치 접속·송신·설정 변경은 하지 않았다.

> **최신 결과:** Arduino GND를 계기판 GND에 직접 연결한 뒤 UPPERPIN/LOWERPIN에서 정상 프레임 30/116개, `55` 0개를 확인했다. LOWER의 ODO 36,475km는 실제 표시와 일치한다. [접지 변경 후 양방향 검증](2026-09-10-upper-lower-uart-confirmed.md). 이 문서의 0개 결과는 초기 두 TSV만의 결과다.

> **후속 결과:** 별도로 제공된 Agilent CSV에서 `F5 A1 02 01 07 50` 정상 프레임을 115200/8N1로 복원했다. Low 구간의 높은 전압·흔들림도 확인했다. [실제 파형 분석](2026-09-10-agilent-scope-uart-decode.md)을 우선 참고한다. 아래 두 TSV에서 유효 프레임이 없었다는 결과는 그대로이며, CSV와 같은 순간의 캡처로 간주하지 않는다.

## 결론

두 파일 모두 수신 바이트의 약 85%가 `0x55`이고, 알려진 Noodoe UART의 **정상 F5 프레임을 확보하지 못했다.** `F5` 시작 바이트, 길이, XOR 체크섬을 검사한 결과 두 파일 모두 체크섬이 맞는 프레임은 0개다. 따라서 현재 로그에서 속도·ODO·연료량을 확정 추출할 수 없다.

두 번째 파일에는 `F5 21 09` 헤더가 한 번 있다. 이 점은 알려진 차량 상태 메시지와 닮은 흔적이지만, 뒤의 체크섬이 틀려 정상 수신을 입증하지 못한다. 캡처·전기적 신호·보레이트/포맷·실물 펌웨어 차이를 구분하려면 실제 파형과 대조해야 한다.

## 사용자 제공 조건과 파일 범위

- 별도 장치인 2017 AK550 차량 계기판과 Noodoe를 연결하여 정상 동작시키며 관측했다.
- 사용자는 두 파일을 각각 TX/RX 선의 캡처라고 설명했다. **어느 파일이 어느 장치의 송신인지 이름만으로는 미확인**이다.
- 사용자는 측정한 UART 신호가 5V라고 보고했다. 오실로스코프 원본 파형은 이번 분석에 없다.
- **후속 확인:** 사용자는 한 비트가 약 8µs임을 오실로스코프로 이미 확실히 측정했다고 정정했다. 비트 폭은 미측정 항목으로 다루지 않으며 같은 측정을 다시 요구하지 않는다. 사용자가 표현한 약 8µs를 더 정밀한 수치로 임의 변환하지 않았다.
- 사용 장비는 메인 ATmega328P를 뺀 정품 Uno의 내장 USB–UART이다. 앞서 안내한 수신 연결은 D1/TX와 공통 GND이며, D0/RX는 연결하지 않는 구성이다. 실제 결선 사진은 검토하지 않았다.
- 파일명은 COM11 / 115200 / 8N1을 표시한다. 이는 캡처 설정 표기이며 실제 선로 baud를 측정한 값은 아니다.
- TSV의 `Direction=Rx`는 PC 측 수신 방향이다. 이것을 Noodoe RX 또는 차량 계기판 RX로 단정하지 않았다.
- 최초 조회에는 040831 파일만 있었고, 사용자가 두 번째 파일 저장을 알린 뒤 두 파일을 모두 분석했다.

첫 파일은 하위 니블이 `5`인 바이트가 3,969개(93.08%)이고, 최하위 비트가 1인 바이트가 4,249개(99.65%)다. `55/B5/D5/95/F5`처럼 교대 비트에 치우친 값이 많다. 이것을 무작위 잡음이라고 단정하는 것도 적절하지 않다.

원본 SHA-256:

```text
040831: 73f8601ad3c8cd874ccb6449e40a0ec7a5e14f2d8cf920f206864b994e236a0c
040913: fbe8b30dbbf89e39098548aa7445501fbe1211eae1fbc9efafd7198d5ccd5a5c
```

파서는 `Data` 열만 추출했다. Seq, 시각, DeltaMs, ASCII 표시를 HEX로 다시 해석하지 않았다. USB/프로그램의 수신 청크 경계를 넘어 스트림을 이어 붙이고 모든 `F5` 위치를 검사했다. 행의 4/12/16ms 간격은 호스트 수신 시각이므로 선로 비트 폭이나 실제 패킷 주기로 사용하지 않았다. 첫 행의 38,922.9ms Delta도 파일에 없는 앞선 이벤트와의 간격일 수 있다.

## 두 번째 파일의 F5 21 09 후보

추출 바이트 오프셋 4411(0부터), 원본 TSV 243행, Seq 1776, 시각 04:09:04.826:

```text
F5 21 09 | 50 54 54 00 7B 8E 80 00 54 | 7C
  헤더              9바이트 payload       기록된 checksum

F5부터 마지막 payload까지 XOR = AC
기록된 checksum                = 7C
```

따라서 이 후보를 정상 차량 상태로 해석하지 않는다. 체크섬을 제외한 시작 위치를 CMD/LEN/payload로 바꾸거나 단순 sum8을 적용해도 이 후보의 `7C`를 일관된 방식으로 설명하지 못했다. 다른 `F5 21` 후보의 LEN은 `19`(25)와 `49`(73)로, 펌웨어에서 확인한 9바이트 차량 상태와 다르다.

임의의 단일 비트를 고치거나 예상 ODO를 맞춰 값을 복원하면 여러 해답을 만들 수 있다. 이번 분석에서는 그런 추정값을 실측 데이터로 만들지 않았다.

## 55가 뜻하는 것과 아직 모르는 것

`0x55`는 `01010101`인 **한 바이트**다. 일반적으로 교대 비트 패턴은 baud 측정/동기화에 쓰일 수 있으며 ST의 자동 baud 검출 예제에도 0x55 모드가 있다. 하지만 이것은 이 계기판이 그런 기능을 사용한다는 증거가 아니다. [ST AN4908](https://www.st.com/resource/en/application_note/an4908-getting-started-with-usart-automatic-baud-rater-detection-for-stm32-mcus-stmicroelectronics.pdf)

기존 V5.16의 차량 UART 송수신 코드에서 확인된 프레이밍은 `F5 | CMD | LEN | PAYLOAD | XOR`다. 확인한 parser/builder에는 `55`를 프리앰블로 삽입하거나 제거하는 근거가 없다. 전체 펌웨어나 실물의 다른 버전에 그런 동작이 없음을 증명한 것은 아니다.

현재 가능한 설명은 다음과 같고, 확률 순위까지 정할 자료는 없다.

- 실제 선로에 55 또는 규칙적인 파형이 존재한다.
- baud/포맷/극성이나 신호 품질 때문에 USB–UART가 다른 바이트로 해석한다.
- 선택한 선의 기능 또는 실물 탑재 펌웨어/전기적 인터페이스가 분석한 V5.16 경로와 다르다.
- 캡처 프로그램이나 USB–UART 구간에서 데이터가 달라진다.

일반 UART는 송수신 baud·데이터 비트·패리티·stop 설정이 맞아야 한다. 파일명만으로 실제 설정과 파형의 일치를 보장할 수 없다. [Microchip UART 설정 설명](https://developerhelp.microchip.com/xwiki/bin/view/products/mcu-mpu/32bit-mcu/ap-exercises/lab7/step1/)

**후속 검토 — Uno 캡처의 오류 정보 한계:** Arduino 공식 `Arduino-usbserial.c`의 `USART1_RX_vect`는 `UDR1` 바이트만 ring buffer에 넣는다. 이 경로는 FE1(프레이밍 오류)·DOR1(오버런)·UPE1(패리티 오류) 상태를 함께 읽거나 PC에 전달하지 않는다. 따라서 이 코드와 같은 순정 USB 변환 펌웨어를 사용하는 경우, HEX만으로 정상 바이트와 오류를 동반한 바이트를 구분할 수 없다. 실제 Uno에 탑재된 정확한 펌웨어 버전은 확인하지 않았다. 이 사실은 프레이밍 오류가 이번 원인임을 증명하지 않지만, 이미 확인된 비트 폭과 불완전한 HEX 수신이 양립할 수 있음을 설명한다. [Arduino 공식 소스, 수신 ISR](https://raw.githubusercontent.com/arduino/ArduinoCore-avr/master/firmwares/atmegaxxu2/arduino-usbserial/Arduino-usbserial.c)

두 장치가 정상 동작했다는 사용자 관측을 존중한다. 현재 파일의 비정상 프레임만으로 장치 간 통신 자체가 고장 났다고 주장하지 않는다.

바이트 단위 반전, 비트 순서 반전, 두 변환의 조합, XOR 55/AA를 진단적으로 적용했지만 알려진 CMD·예상 길이·XOR가 모두 맞는 프레임은 없었다. `55`를 모두 제거해도 알려진 정상 프레임은 0개다. 제거한 첫 파일에는 미확인 CMD로 단순 XOR가 맞는 후보 한 개가 생기지만, 임의 변환 뒤의 우연한 checksum 일치로 취급하며 복구 결과로 쓰지 않는다. 바이트 반전은 UART start/stop을 포함한 원래 파형의 극성 반전 후 재디코딩과 동등하지 않다.

## 다음 측정

사용자가 이미 비트 폭을 확인했다는 정정을 반영하여, 이전의 비트 폭 재측정 제안은 철회했다. 다음 확인은 입력과 수신 경로를 분리하는 목적이다.

1. USB–UART/프로그램만 점검하려면 **차량 신호선을 Uno에서 분리한 후** Uno D0–D1 loopback으로 `00 FF 55 AA F5 21 09` 같은 HEX 패턴이 그대로 되돌아오는지 확인한다. 이는 PC/변환기 경로의 기본 검사이며, 같은 칩의 TX/RX가 같은 클록을 사용하므로 변환기의 절대 baud 정확도나 차량 쪽 신호 품질을 검증하지는 않는다. 이번 분석에서는 실행하지 않았다.
2. 고정 입력에서 예상치 못한 바이트가 생기는지 분리하려면, **차량 신호선과 D0를 D1에서 완전히 분리하고 USB로 전원 공급한 Uno의 D1을 Uno 자체 5V에 연결**하여 수신 입력을 정상 idle인 High로 고정할 수 있다. 기존 버퍼를 비운 뒤에도 새 55가 계속 기록된다면 실제 차량 신호 외의 캡처/COM/변환기 경로를 조사한다. 정지했다고 실제 차량 바이트가 올바르게 디코딩됨을 보장하지는 않는다. 차량 신호가 붙은 상태에서 5V에 고정하지 않는다.
3. 파형을 추가 검토할 경우 관찰 대상은 **우노 D1–GND에서의 idle 극성, start/stop 정렬, Low/High 레벨**이다. D0 미연결과 공통 GND도 확인한다. scope의 UART 디코딩 기능이 있으면 같은 구간을 Uno 로그와 비교한다. 비트 폭을 다시 재는 작업과는 목적이 다르다.

TX/RX 양쪽을 다시 기록할 때는 `dash_tx_to_noodoe_rx`, `noodoe_tx_to_dash_rx`처럼 **송신 장치를 명시**하고, 장치를 켠 직후와 정상 동작 구간을 구분해 두면 후속 분석에 도움이 된다.
